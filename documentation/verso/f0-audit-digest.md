# Auditoría del stack actual (5 áreas)

## fork-internals — @wordjs/puck (frontend/packages/puck), fork vendorizado de @measured/puck v0.20.2

**Resumen:** El fork es ~14.527 LOC TS/TSX + 2.421 LOC CSS (16.948 fuente real, sin dist/) repartidas en ~150 ficheros. Divergencia real de upstream: EXACTAMENTE 5 sitios marcados `WORDJS` en 2 ficheros (verificado por grep exhaustivo, coincide con lo que pinea `puckForkDivergence.test.ts` y enumera `NOTICE.md`) — nada más en el fork es custom. Divergencia 1 (4 sitios en DraggableComponent + 1 en Preview): la capa de overlay del editor (selección + ActionBar) se portalea a `[data-puck-overlay-layer]` en el documento PADRE (vía `frameElement`) en vez de al `<body>` del iframe — geometría 1:1 sin término de scroll ni división de escala, re-sync en scroll/resize capture-phase. Divergencia 2: acción "Edit" en el ActionBar solo para `componentType==="Text"|"Heading"` que llama `window.puckSetActiveEditorId(id)` (global instalado por `frontend/src/components/PuckEditor.tsx`, el wrapper de ~2160 líneas). El resto del paquete es upstream v0.20.2 sin tocar. Arquitectura: zustand (store/index.ts, `subscribeWithSelector`) + reducer clásico de 11 tipos de acción + 4 slices (history/permissions/nodes/fields) + dnd-kit NUEVO (`@dnd-kit/react` 0.1.18 + `@dnd-kit/dom/abstract/geometry/collision/state`, NO el `@dnd-kit/core` clásico) con un plugin propio (`NestedDroppablePlugin`) para resolver la zona más profunda bajo el puntero. Modelo de datos dual: zonas legacy (`Data.zones: Record<string, Content>`) + slots modernos (`type:"slot"` dentro de `props`, resuelto por `mapFields`/`walkTree`/`useSlots`), con migración automática (`migrate.ts`, 2 pasos) de zonas→slots que FALLA DURO si un slot no existe en el config del componente. `data` NO es un prop controlado: se copia UNA VEZ al montar (`useState(() => createAppStore(...))` en `PuckProvider`); cambios posteriores al prop `data` nunca se releen — la única vía de entrada tras el mount es `dispatch`. `resolve()` por componente es async y se dispara tanto en el store (resolución incremental en vivo, `resolveAndCommitData`) como en un util standalone puro (`lib/resolve-all-data.ts`, para SSR/publish fuera del editor).

**Reutilización:** Por subsistema (reutilizable tal cual / adaptable / reescribir):

REUTILIZABLE TAL CUAL (baja o nula dependencia del store/dnd, contrato ya consumido por 31 plugins/64 temas): Render + SlotRender (+server.tsx) — CERO import de useAppStore, es el mismo camino de publicación/SSR del sitio público; tocarlo es tocar todo lo publicado. AutoFrame — solo depende de portales React/DOM, sin acoplo al AppStore; la lógica de copiar estilos al iframe (MutationObserver+hash-dedupe) es infraestructura genérica sin conocimiento de WordJS. lib/get-class-name-factory.ts — trivial, adoptar o alinear con wordjs-ui.css existente. Field/FieldProps (el TIPO, no necesariamente la implementación) — 31 plugins + bloques core ya declaran sus props contra esta union de 9 tipos; cambiarla es una migración masiva, no una decisión de diseño del editor nuevo.

ADAPTABLE (arquitectura vale la pena conservar, implementación necesita poda): AutoField + fields/* (ArrayField/ObjectField/ExternalField/...) — genérico, config-driven, sin acoplo a dnd/canvas; reusar casi verbatim los renderers, pero simplificar el contrato NestedFieldContext. La capa de overlay-portal-en-documento-padre (Divergencia 1) — el DISEÑO (chrome inmune al CSS de la página editada) es correcto y ya validado; en un editor desde cero esto deja de ser una rama especial (frameElement + hasAttribute + fallback) y pasa a ser el ÚNICO camino — mayor limpieza, no hay que "adaptar", hay que simplificar. resolve()/resolveAllData/resolve-component-data — capacidad real (contenido dinámico por bloque) que hay que preservar; implementación pequeña y portable. store/slices/permissions.ts — el modelo (permisos dinámicos por-item resolubles) encaja con el sistema de capacidades/roles ya existente de WordJS; conviene puentearlo al backend en vez de reinventarlo. AutoFrame es infraestructura reutilizable pero su style-mirroring vía MutationObserver es frágil si el nuevo editor decide NO usar iframe (decisión de F1 pendiente).

REESCRIBIR (máximo acoplo interno, carga cruft del modelo dual zonas/slots que no aporta valor a un editor desde cero): store/index.ts + reducer/* + lib/data/walk-app-state.ts + lib/data/map-fields.ts — el motor de indexación es el corazón más entrelazado del fork (cada acción recalcula indexes.nodes/zones desde cero); vale la pena conservar el PATRÓN (store único + reducer tipado + índices derivados) pero no el código, porque arrastra el modelo dual zonas-legacy/slots-modernos que ya está siendo migrado. dnd/* completo (NestedDroppablePlugin 293L + collision/dynamic 184L + collision/directional 56L + use-sensors 64L) + DragDropContext (607L) — es el comportamiento MÁS valioso a preservar (resolución de zona más profunda, inserción RTL-aware, commit gateado por animación, distinción nuevo-vs-existente) pero está escrito directamente contra el vocabulario zoneCompound/areaId/depthIndex de Puck; es también el bloque de código más complejo y con más riesgo de regresión del fork entero (~1200 líneas de geometría/colisión) — presupuestar F2 en consecuencia. migrate.ts — es Puck-version-específico; el editor nuevo necesita el CONCEPTO (migraciones de datos versionadas) no este código, salvo quizá un backfill puntual de la migración #1.

ACOPLAMIENTOS QUE OBLIGAN A ABSORBER EN BLOQUE: (1) DraggableComponent↔DropZone↔DragDropContext↔ZoneStoreContext↔NestedDroppablePlugin↔detectores de colisión dnd-kit — clúster inseparable de ~2.700 líneas; no se puede extraer DraggableComponent sin el contrato de registro de zona de DropZone NI el ZoneStoreContext (que es un store zustand DISTINTO del AppStore) NI todo el cableado dnd-kit. (2) store/index.ts↔reducer/*↔walk-app-state+get-item+mapFields↔types/Internal.PrivateAppState.indexes — otro clúster inseparable; cada acción del reducer llama de vuelta a walkAppState y cada selector lee state.indexes. **Contratos duros:**
- Forma de Data que Render/SlotRender consumen para publicación/SSR: {root:{props:{...}}, content: ComponentData[], zones?: Record<zoneCompound, ComponentData[]>} donde ComponentData={type:string, props:{id:string,...}}; los campos type:'slot' anidan Content directamente dentro de props[slotName]. Cualquier editor nuevo debe seguir emitiendo datos que Render pueda consumir sin cambios, o aportar una migración explícita para las páginas/temas/plugins existentes.
- Union Field/FieldProps (9 tipos: text, number, textarea, select, radio, array, object, external(+adaptor deprecado), custom, slot) — es el contrato de campos editables que YA declaran el bloque core y los 31 plugins de marketplace; cambiar nombres/forma de tipo rompe cada config de bloque existente.
- Firma de ComponentConfig.render(props) recibiendo puck:{renderDropZone, isEditing, dragRef, metadata} + props aplanadas + id — firma contra la que cada bloque (core y de plugin) ya está escrito.
- Firmas async de ComponentConfig.resolve / resolvePermissions / resolveFields — hooks reales que bloques existentes pueden estar usando para contenido/permite dinámico.
- props.id único generado una vez (uuid vía generateId) al insertar o migrar, usado como clave en indexes.nodes y como valor de data-puck-component/data-puck-dnd en el DOM — no se puede regenerar por-render sin romper selección/DnD/overlay.
- El prop `data` de <Puck> NO es controlado tras el mount (se copia una vez a un useState inicializador); un editor nuevo debe decidir explícitamente si preserva este contrato (dispatch como única vía de escritura, con onChange como única vía de lectura hacia afuera) o lo rompe deliberadamente — pero PuckEditor.tsx HOY depende del patrón no-controlado (fallback local + window.puckDispatch) y ese wrapper necesitaría reescritura si cambia.
- overrides.actionBar recibe {label, children, parentAction} pero NUNCA id/componentType — limitación real de la API pública de Puck que forzó la Divergencia 2 vía window global; un editor nuevo debería resolver esto pasando id/type de forma nativa en vez de reproducir el workaround.
- NOTICE.md exige que CUALQUIER divergencia futura del fork quede marcada con comentario WORDJS grepable y enumerada en el propio NOTICE.md, pineada por frontend/src/lib/__tests__/puckForkDivergence.test.ts — esto es una norma de proceso del proyecto (transparencia de fork), no código, pero aplica igual a cualquier reescritura que se declare 'basada en Puck' o que mantenga compatibilidad de datos con él.
- Suite de test de contrato del wrapper (puckEditorWrapper.test.ts) pinea contra el CÓDIGO FUENTE (no comportamiento) de PuckEditor.tsx: piso de autosave 8000/30000ms, dispatch vía window.puckDispatch con {type:'setData', data:transform, recordHistory:true}, y el global window.puckSetActiveEditorId — cualquier reemplazo de PuckEditor.tsx que no actualice/retire este test dejará una suite verde mintiendo sobre un editor que ya no existe.

- Cobertura de test real casi nula: el 95% del wrapper (todo excepto undo/redo) no tiene ningún test que ejecute comportamiento — solo pines de texto fuente que se invalidan con cualquier refactor, dando una falsa sensación de red de seguridad (los pines pasan mientras el TEXTO no cambie, no mientras el COMPORTAMIENTO no cambie).
- Dos editores (PuckEditor.tsx para page/post vs Puck directo para chrome) ya DIVERGEN en features hoy — un rewrite que trate 'el editor' como una sola superficie puede pasar por alto que /admin/chrome necesita su propia decisión de diseño, no solo un port mecánico.
- La gracia post-mount de 800ms (heurística temporal para distinguir ruido de inicialización de una edición real del usuario) está DUPLICADA idéntica en pages/[id] y posts/[id] — un rewrite que la centralice mal, o que cambie el timing de Puck, puede reintroducir el bug que originó el guard (primera edición real del usuario silenciosamente ignorada).
- La regeneración de fallback HTML (contentRef) para el campo legacy `content` está DUPLICADA y ya DIVERGENTE entre pages (soporta Card/Divider/Button) y posts (no los soporta) — evidencia de que la duplicación ya causó drift real, no solo riesgo teórico; un motor nuevo debe centralizar esto o heredará el mismo bug.

- Múltiples setInterval de larga vida (700ms×2, 400ms, 1000ms, 10000ms×2) corren durante TODA la sesión del editor para reafirmar CSS/enlaces/hotkeys contra un iframe que Puck's AutoFrame puede recargar en cualquier momento — funciona pero es una solución de polling costosa y fértil en condiciones de carrera; un motor nuevo con un ciclo de vida de iframe más predecible podría eliminar toda esta clase de código.
- Dependencia de window.__PUCK_INTERNAL_DO_NOT_USE (literalmente nombrado 'no usar' por el propio fork) en 3 sitios de producción (ActionBarOverride.move, selectBlockById, CommandPalette readSelected/readSelector) — un bump de versión del fork que reestructure sus internals degrada estas 3 features SIN CRASH (fail silencioso: los botones Subir/Bajar simplemente dejan de clampear, el a11y panel deja de seleccionar el bloque).
- El heartbeat de presencia (fetch inline a /api/v1/presence/:pageId cada 10s) está hardcodeado dentro de PuckEditor.tsx en vez de pasar por lib/api.ts como el resto del código — inconsistencia de capas que un rewrite debería corregir, no replicar.
- Guardia de permisos (can('edit_posts')) existe SOLO en pages/[id], NO en posts/[id] — asimetría de seguridad-por-UX ya presente hoy (el backend sigue siendo la autoridad real vía capability-gating en POST/PUT /posts, pero el editor de posts se abre por URL directa sin bloqueo de UI para un usuario sin permiso).

**Contratos duros:**
- Forma de _puck_data en meta: exactamente el Data de @wordjs/puck ({content:[...], root:{props:{...}}}), pasado por migrate(data, config) al cargar; el motor nuevo debe seguir produciendo/consumiendo esta forma o romper la interop con contenido ya guardado.

**Riesgos:**
- Si el editor nuevo NO reutiliza blockShell.ts (hideClasses/animClasses/appearanceToStyle) y reimplementa esa lógica 'equivalente', CUALQUIER discrepancia de redondeo/orden de propiedades/nombres de clase rompe TODAS las páginas ya guardadas con `look`/`anim`/`hide` en su _puck_data — no hay migración posible porque el servidor público seguiría usando la implementación original vía SharedBlockShell mientras el editor mostraría algo distinto (drift editor/público, justo lo que el diseño actual evita a propósito)
- El campo `css` (arbitrario, spreadeado DESPUÉS de blockVars) es un escape hatch de máxima prioridad presente en LOS 30 BLOQUES — si el editor nuevo omite ese campo en algún bloque migrado, cualquier página que lo use pierde sus estilos custom silenciosamente (no hay error, el objeto simplemente deja de aplicarse)
- blockVars() OMITE valores vacíos deliberadamente (contrato central: autor>tema>fallback). Un editor nuevo que 'simplifique' emitiendo siempre un valor (aunque sea el default) ROMPE el theming: fijaría cada bloque a su valor default para siempre y ningún tema podría volver a tocarlo — es el bug exacto que este contrato fue creado para eliminar (~100 !important por tema antes)
- CONTAINER_TAGS/CLASS_TOKEN están validados en TRES lugares independientes por diseño defensivo (blocks.tsx runtime, backend template-validate.ts, frontend lib/templateData.ts mirror) precisamente porque _puck_data es AUTHOR-CONTROLLED y ya produjo un stored-XSS real (level:'script' en HeadingBlock, documentado en el código). Un editor nuevo que introduzca un nuevo prop 'estructural' (elige tag/elemento) SIN pasarlo por un allowlist Set repite esa clase de vulnerabilidad
- HEADING_TAGS es la ÚNICA defensa contra que `level` elija un tag arbitrario incluyendo <script> o tags void que hacen 500 en SSR — cualquier reimplementación de Heading que use `level` directamente como nombre de tag sin ese Set reintroduce el CVE ya documentado
- El wrapper de 2 capas anidadas (animación en el exterior, apariencia+overlay en el interior) es DELIBERADAMENTE así porque animation-fill-mode:both fijaría transform:none tras la entrada y mataría cualquier :hover si compartieran elemento — colapsar a 1 sola capa en el editor nuevo por 'simplicidad' rompe silenciosamente el hover en cualquier bloque con animación de entrada Y hover configurados a la vez (combinación común: casi todo bloque nuevo trae anim:fade-up por defecto)
- VideoEmbed valida el host del iframe contra un allowlist ANTES de renderizar (mismo patrón que lib/sanitize.ts isAllowedIframeSrc) — un editor nuevo que reconstruya el parseo de URL de YouTube/Vimeo sin repetir esa validación exacta reabre el vector de iframe arbitrario/javascript: URL
- asimetría postConfig.root.fields vs pageConfig.root.fields (SEO/category/allowComments solo en post) es fácil de perder de vista y colapsar 'por consistencia' en un editor nuevo — sería un cambio de comportamiento del CMS, no solo del editor
- Symbol depende de que baseConfig.components exista como mapa VIVO en el momento de primer render (getter con late binding documentado explícitamente) — un editor nuevo con otro ciclo de vida de configuración (ej. config inmutable calculada una vez) puede romper Symbol si el mapa se congela antes de que withSharedBlockFields lo haya envuelto
- 12 tipos de animación de entrada están declarados en el tipo AnimSpec pero solo 5 keyframes (fade,fade-up,fade-left,fade-right,zoom) fueron confirmados en el rango de wordjs-ui.css leído (offset 1029-1054) — falta verificar si fade-down/zoom-out/blur/rise/flip/reveal/swing tienen @keyframes más abajo en el archivo (2692 líneas totales); si no los tienen, esos 7 tipos son actualmente NO-OP visual en producción y un editor nuevo podría 'confirmar el bug' asumiendo que están completos sin verificar en el navegador
- El bloque Form usa namespace `wjs-form*` en vez de `wp-block-form*` — inconsistencia real del sistema actual (no error mío): un editor nuevo que asuma 'todo bloque es wp-block-<nombre>' para generar CSS de tema automáticamente fallará silenciosamente en Form
- PluginBlockIsland/PluginBlockHeavy (bloques de marketplace + Symbol) NO se renderizan en el servidor — pintan tras hidratación; un editor nuevo que intente SSR-completo 'por defecto' para paridad visual con el público debe replicar este trade-off documentado, no asumir que puede eliminarlo sin costo de bundle

- ColumnsBlock: máximo 3 columnas físicas (slots col-0/col-1/col-2) es un límite estructural actual — cualquier editor nuevo que permita más columnas por UI sin cambiar este límite de render las descarta silenciosamente

- onClick preventDefault en enlaces/botones (Button, PricingTable, CTABanner, SocialLinks, PostsGrid, CategoryPosts, Hero) debe seguir condicionado a `isEditing` (nunca presente en el árbol renderizado por el servidor) — es lo que evita que un clic en el canvas navegue el iframe sin añadir un handler inútil (y potencial fuente de hydration mismatch) al HTML público

## data-security-pipeline

**Resumen:** _puck_data es un JSON {content: Item[], root:{props,title?,slug?}, zones?:{}} persistido tal cual (JSON.stringify) en post_meta.meta_value bajo la clave '_puck_data'. Backend/src/core/sanitize-meta.ts (sanitizePuckTree, L53) es el ÚNICO punto de saneo de escritura, compartido entre routes/posts.ts (POST/PUT /posts, POST /posts/:id/meta) y core/wxr-import.ts: recorre recursivamente TODO el árbol preservando su forma, y clasifica cada hoja string por el NOMBRE de la clave que la contiene (keyHint): las claves {content,html,text,title,heading,description,caption,body} pasan por sanitize() (sanitize-html con allowlist ampliado img/h1/h2/iframe + allowedIframeHostnames youtube/vimeo); TODA otra hoja string (URL-fields explícitos o no) pasa por safePuckUrl, que solo blanquea si el valor empieza por javascript:/data:/vbscript:/file: tras stripear bytes de control — todo lo demás (rutas relativas, clases, colores, iconos FontAwesome) sobrevive intacto. Post.updateMeta hace UPDATE-then-INSERT por (post_id,meta_key): el merge de `meta` en PUT /posts/:id es por CLAVE COMPLETA — omitir una key la deja stale, enviar '' la limpia; no hay merge profundo dentro de _puck_data (guardar el árbol es sustituir el árbol entero). saveRevision copia post_meta completo (incluido _puck_data íntegro) a una fila post_type='revision'; se salta SOLO cuando el PUT trae body.autosave===true, para no agotar el cupo de 10 revisiones con guardados periódicos de fondo. WXR import/export preserva _puck_data re-saneándolo (sanitizeImportedMeta); el backup completo del sitio (import-export.ts) lo exporta verbatim sin re-sanear. Render público: ContentRenderer.tsx (server component) lee solo data.content — data.zones es un vestigio del runtime interno de Puck, no se usa en render — despacha 21 tipos de bloque core por switch a componentes compartidos en blocks.tsx (mismos componentes que usa el canvas del editor, vía SharedBlockShell); cualquier tipo no reconocido (plugin/Symbol) cae a PluginBlockIsland (client-lazy). Los únicos 3 sumideros dangerouslySetInnerHTML en el árbol de bloques (Heading.title, HTMLEmbed.html, Text.content) pasan además por frontend/src/lib/sanitize.ts, isomórfico (DOMPurify en cliente, sanitize-html puro-JS en servidor vía __non_webpack_require__) — doble capa de saneo (escritura + lectura). /preview/[slug] es ruta separada force-dynamic gateada por sesión (autor/editor, 404 a otros) que envuelve con el MISMO ThemeTemplate que /[slug] (ISR revalidate=60 + generateStaticParams). La purga on-demand (core/frontend-purge.ts) escucha los hooks post_updated/wp_insert_post/deleted_post que SOLO disparan Post.update()/Post.create() — no Post.updateMeta() directo — y hace POST autenticado (HMAC timing-safe, fail-closed) a /api/revalidate del frontend. El único riesgo es de PERFORMANCE: _puck_data de páginas grandes se duplica íntegro en cada revisión sin compresión ni diffing — aceptable hoy (cap de 10), a vigilar si el editor nuevo permite documentos mucho más grandes.\n\nwxr-import.ts (sanitizeImportedMeta): REUTILIZABLE TAL CUAL — delega en sanitize-meta.ts, comportamiento correcto documentado.\n\nimport-export.ts (backup de sitio): REQUIERE AUDITORÍA ADICIONAL antes de confiar — el export no re-sanea (asume que ya fue saneado al escribir, lo cual es cierto SI todo write path pasa por sanitizeMetaValue, pero es una asunción implícita no verificada aquí en el lado de IMPORT de este módulo específico).\n\nfrontend-purge.ts + /api/revalidate: REUTILIZABLE TAL CUAL — el mecanismo de purga está desacoplado del formato de _puck_data (opera sobre tags/paths genéricos de post), pero el editor nuevo DEBE seguir dependiendo de que su(s) endpoint(s) de guardado disparen post_updated (vía Post.update()) — si introduce un endpoint de autosave granular que llame Post.updateMeta directo, DEBE añadir el disparo de purga explícitamente (gap ya existe hoy en POST /posts/:id/meta, simplemente no se usa en el flujo actual).\n\nContentRenderer.tsx + blocks.tsx + SharedBlockShell: REUTILIZABLE COMO CONTRATO, el código en sí es específico del catálogo de 21 bloques core actuales — un editor nuevo que cambie el catálogo de bloques o su forma de props DEBE mantener el patrón (mismo componente de render para canvas y público, un switch central de tipo→componente, slots como arrays en props no como 'zones') pero reescribirá el contenido del switch. El patrón arquitectónico (server component + islands solo para lo interactivo) es sólido y debe preservarse.\n\nsanitize.ts (frontend, DOMPurify/sanitize-html isomórfico): REUTILIZABLE TAL CUAL — es genérico, no depende de la forma de _puck_data, ya cubre los 3 sumideros existentes y cualquier sumidero nuevo del editor debe simplemente llamarlo.\n\nFlujo de guardado en admin/posts/[id]/page.tsx: ADAPTABLE — la LÓGICA (leer store live, autosave flag, salvaguardas de hidratación y de contenido legacy) debe preservarse conceptualmente en el editor nuevo, pero el código en sí está acoplado al Puck fork actual (window.puckGetData/puckCommitActive) y se reescribirá junto con el editor.

**Riesgos:**
- El allowlist PUCK_HTML_FIELDS/PUCK_URL_FIELDS es una lista de nombres de clave FIJA y CERRADA (8+6 nombres) — cualquier bloque nuevo (core o de plugin) que use un nombre de campo HTML no listado (richText, markup, excerpt, etc.) queda SIN SANEAR en escritura; el editor nuevo debe reutilizar exactamente estos nombres, extender ambos Sets, o mover el saneo a un mecanismo schema-driven por-bloque
- safePuckUrl es deliberadamente PERMISIVO (solo bloquea 4 schemes peligrosos) — no es una validación de URL real; cualquier endurecimiento debe hacerse con mucho cuidado porque ya rompió el page builder una vez históricamente (blanqueaba rutas relativas/fragmentos)
- POST /posts/:id/meta bypassa la purga ISR (no dispara post_updated) — si el editor nuevo usa autosave granular por-key en vez de PUT completo del post, DEBE disparar purgeForPost explícitamente o el contenido publicado quedará hasta 60s desactualizado sin que nadie lo note en dev (autosave hoy usa el mismo PUT completo, así que el gap está latente, no activo)
- El merge de meta es por-clave completo, NO profundo dentro de _puck_data — un guardado que mande un _puck_data PARCIAL (patch en vez del árbol completo) sería tratado como el árbol NUEVO completo, perdiendo silenciosamente todo bloque no incluido en el patch; el editor nuevo NO puede introducir un modo de guardado incremental de _puck_data sin cambiar este contrato explícitamente
- restoreRevision reemplaza TODO post_meta del post padre con el snapshot de la revisión (DELETE+INSERT) — cualquier meta key añadida DESPUÉS de esa revisión (por el editor nuevo o por un plugin) se pierde al restaurar, no solo _puck_data
- import-export.ts (backup completo del sitio) no re-sanea en el export; el lado de IMPORT de ese módulo no fue leído en detalle en esta auditoría — verificar antes de asumir que es un camino de escritura cubierto por sanitizeMetaValue
- sanitizePuckTree es recursivo SIN límite de profundidad visible en el código leído — un _puck_data adversarial con anidamiento extremo podría causar stack overflow en el saneador de escritura (server-side, afecta disponibilidad)
- Inconsistencia de allowlist de hosts de iframe entre 3 lugares (backend sanitize(): 2 hosts; frontend sanitize.ts: 2 hosts; VideoEmbedBlock: 4 hosts incluyendo youtube-nocookie.com) — no es una vulnerabilidad activa (todos son subconjuntos seguros) pero es deriva de configuración que el editor nuevo debería consolidar en una única fuente de verdad
- Un campo de plugin con nombre HTML no reconocido (fuera de PUCK_HTML_FIELDS) depende ENTERAMENTE de que el propio componente de render del plugin llame sanitizeHTML en su sumidero — el backend no puede protegerlo; es la frontera de confianza plugin↔core más débil de todo el pipeline y no está reforzada estructuralmente

**Contratos duros:**
- Forma JSON exacta: {content: Array<{type:string, props:{id:string,...}}>, root:{props:{...}, title?, slug?}, zones?:{}} debe preservarse byte-exactamente en round-trip para no romper documentos ya guardados en producción
- meta._puck_data se persiste como JSON.stringify() en post_meta.meta_value y se reconstituye con JSON.parse() en cada lectura (con fallback a string crudo si el parse falla) — cualquier valor no serializable en JSON se pierde silenciosamente
- item.type DEBE ser uno de los 21 strings reconocidos por el switch de ContentRenderer.tsx (Heading,Text,Image,Divider,Button,Spacer,Section,Grid,FlexRow,Columns,Card,Quote,Table,IconList,SocialLinks,Stats,HTMLEmbed,PricingTable,Testimonial,CTABanner,VideoEmbed,Hero,PostsGrid,CategoryPosts,AudioPlayer,Accordion,Tabs,SearchBar,Form,Symbol) o cae a PluginBlockIsland — renombrar tipos core sin migración rompe el render público de contenido ya guardado
- Los nombres de campo de props saneados como HTML en escritura son EXACTAMENTE {content, html, text, title, heading, description, caption, body} (case-insensitive) — un bloque nuevo con campo HTML debe usar uno de estos nombres o extender PUCK_HTML_FIELDS
- TODA hoja string que no sea HTML-field pasa SIEMPRE por safePuckUrl (no solo las 6 en PUCK_URL_FIELDS) — el editor nuevo no puede asumir que un campo arbitrario 'queda sin tocar'; siempre se filtra por scheme peligroso salvo que sea HTML-field
- Merge de meta en escritura es por CLAVE COMPLETA vía UPDATE/INSERT en post_meta: omitir una key del objeto `meta` enviado la deja STALE (no se borra); enviar '' la LIMPIA; no existe hoy una operación de 'delete meta key' expuesta directamente vía el payload de PUT
- autosave:true (boolean literal true, comparado con !==true) en el body de PUT /posts/:id es la ÚNICA señal que salta saveRevision — el editor nuevo debe seguir mandando este flag exacto en cada autosave de fondo o agotará el cupo de 10 revisiones
- saveRevision es fire-and-forget en el create (.catch(console.error)) y no-abortante en el update — un fallo de snapshot de revisión NUNCA debe bloquear ni fallar el guardado del post
- El disparo de purga ISR depende de que el write pase por Post.update()/Post.create() (que llaman doAction('post_updated'/'wp_insert_post')) — cualquier endpoint nuevo de escritura de _puck_data debe pasar por esas funciones o disparar purgeForPost(postId) explícitamente, o el contenido publicado quedará hasta 60s stale
- Ningún dangerouslySetInnerHTML en el camino de render de _puck_data puede omitir sanitizeHTML (isomórfico) — y ningún prop puede elegir libremente un tag/elemento HTML sin un allowlist explícito de tags seguros (lección directa y ya remediada del fix de HeadingBlock/HEADING_TAGS)
- sanitize-meta.ts debe seguir siendo el ÚNICO punto de saneo de escritura de _puck_data, compartido entre TODOS los write paths (posts.ts, wxr-import.ts, y cualquier endpoint nuevo) — prohibido reimplementar saneo inline en una ruta nueva
- ContentRenderer.tsx/blocks.tsx (o su equivalente en el editor nuevo) deben seguir siendo la ÚNICA fuente de verdad de render tanto para el canvas del editor como para el sitio público — mismo componente en ambos lados, o el canvas divergirá de lo publicado
- /preview/[slug] debe seguir siendo force-dynamic, gateado por sesión (autor/editor únicamente, 404 a cualquier otro incluido anónimo), con robots noindex y envolviendo con el MISMO ThemeTemplate que la ruta pública — no debe fusionarse con la ruta cacheada
- El secreto de purga (revalidateSecret) debe seguir comparándose con crypto.timingSafeEqual sobre hash SHA-256 de ambos lados (nunca comparación directa de strings) y el endpoint de purga debe seguir fallando CERRADO (503) sin secreto configurado
- Un tema/bloque público JAMÁS envía JS ejecutable (regla ya vigente para el sistema de temas, extensible al editor): todo prop que controle ESTRUCTURA (qué elemento HTML se renderiza) requiere un allowlist explícito en el COMPONENTE DE RENDER — el saneador de escritura por diseño solo clasifica HTML-vs-URL, nunca semántica estructural de bloque

## plugin-block-surface

**Resumen:** La superficie de bloques de plugins tiene DOS sistemas paralelos que deben coexistir: (1) BUILD-TIME/dev — frontend/scripts/generate-puck-plugin-registry.js escanea backend/plugins/*/manifest.json (solo 8 plugins in-tree hoy) y genera frontend/src/lib/puckPluginRegistry.ts con imports estáticos; (2) RUNTIME/producción — frontend/src/lib/pluginBundleLoader.ts + useRuntimePuckConfig.ts cargan bundles PRE-COMPILADOS de marketplace/plugins/* (31 plugins, empaquetados por backend/scripts/build-marketplace.js → backend/scripts/build-plugin.js con esbuild) vía fetch+Blob+import() dinámico en un useEffect post-hidratación, y los mergean en el config de Puck. Todo bloque (core o plugin) pasa por withSharedBlockFields (frontend/src/components/puck/VisibilityField.tsx) que inyecta gratis 3 campos compartidos (hide/anim/look) y un wrapper de renderizado — este es el "seam" de mayor apalancamiento que el editor nuevo debe preservar exactamente. El aislamiento de React/host se logra reescribiendo imports (`react`, `@/lib/*`, etc.) a `globalThis.WordJS.*` en build-time (esbuild plugin en build-plugin.js) e inyectándolos en window en runtime (pluginBundleLoader.ts) — la lista HOST_MODULES debe estar sincronizada byte-a-byte entre ambos ficheros o el build falla fuerte (no en silencio). Examinados 4 bloques reales (toscano multi-sin-fields, testimonials single, online-store multi-con-fields, card-gallery con selector custom) más el único plugin con themeSurfaces (faq) y el único con hooks (mail-server): la API de-facto que usan es angosta (5 tipos de campo Puck, fetch-only data loading, CSS inline, sin SSR) pero el contrato de compilación/carga por debajo es intrincado y lleno de trampas ya documentadas en comentarios (cache poisoning, dedupe de promesas, 404 ambiguo, orden de resolución de entry points).

- useRuntimePuckConfig: identidad de config MEMOIZADA con useMemo — un config con identidad nueva en cada render hace que Puck regenere su store completo y React desmonte/remonte TODO el canvas (bug histórico documentado: 'canvas se recargaba en cada keystroke')
- loadRuntimePluginHooks() SOLO corre cuando NODE_ENV!=='development' — en dev el registro build-time YA cubre los hooks estáticamente; en producción (marketplace instalado post-build) es la ÚNICA vía. Documentado riesgo aceptado: una imagen self-built con plugins activos AL MOMENTO del build ejecuta sus registradores DOS VECES (una por cada módulo instance) — inofensivo solo porque las claves `key` hacen la re-registración idempotente
- invokeHookRegistrars: invoca cada export cuyo NOMBRE empiece con literal 'register' y sea function — exports que no cumplan el patrón se ignoran silenciosamente; un register() que lanza excepción se loggea y NO detiene los demás
- addAction/addFilter aceptan un 5º/4º parámetro `key` opcional que hace la registración IDEMPOTENTE (reemplaza en vez de apilar) — sin key, callbacks anónimos se apilan en cada re-registro (duplicados de UI)
- Clasificación de 404 de hooks bundle en 3 causas (none/not-built/unreadable) consultando GET /plugins/registry, para avisar SOLO cuando es un problema real (30 de 31 plugins no declaran hooks — silencio esperado)
- GET /api/v1/plugins/registry devuelve un OBJETO `{plugins:[...]}`, NO un array — bug histórico ya corregido en el cliente (extractRegistryList tolera ambas formas pero el contrato real es el objeto)
- CSS del bloque servido por ruta ESTÁTICA `/plugins/<slug>/dist/component.bundle.css` (express.static con remapeo slug→carpeta), DISTINTA de la ruta API `/api/v1/plugins/:slug/bundle/css` que también existe pero no es la que usa el loader runtime
- Bundle JS servido con ETag+Cache-Control:no-cache (nunca cache inmutable) porque la URL es NO versionada — evita que un plugin actualizado quede invisible un año para clientes con caché
- Slug de la URL admin (manifest.frontend.adminPage.slug, ej. 'youtube') puede DIFERIR de la carpeta real (ej. 'youtube-videos') — resolvePluginDir()/resolveAdminSlugFolder() hacen esa traducción tanto para servir el bundle como el estático /plugins/
- themeSurfaces (manifest.json, opt-in, solo faq lo usa): declara {element, selector, children?, tokens?} — selector DEBE ser compuesto solo de clases bajo `.wjs-p-<slug>-` (sin id/attr/pseudo/universal/lista); children con nombres reservados (hover/focus/mobile/dark/etc) RECHAZADOS por colisionar con nesting del compilador de temas; tokens (si se declaran) deben empezar por `--wjs-p-<slug>-`
- themeSurfaces se funde en el manifest de tokens del tema bajo la clave `plugin:<slug>:<element>`, alcanzable por el compilador de temas SIN cambios (mismo lookup element→selector que usan los elementos core)
- manifest.id debe coincidir EXACTAMENTE con el nombre de carpeta o el build/generación de namespace se rechaza (protege contra derivar un prefijo de un slug falso)
- manifest.isolated debe ser literalmente `true` o build-marketplace.js aborta el empaquetado de ese plugin
- Legacy/canal paralelo NO relacionado con Puck (card-gallery): manifest.frontend.components[]+locations+shortcodes[] + client/editor/*.js estilo Editor.js (toolbox/render/save) — build-plugin.js y generate-puck-plugin-registry.js lo IGNORAN por completo; es una superficie muerta o viva por otro camino no auditado en este informe
- Build determinista: fecha fija (2026-01-01) en entradas de zip, sin build timestamp en manifest.build.json ni en el banner del bundle — reconstruir fuentes sin cambios produce zips byte-idénticos (sha256 estable) para permitir gate CI de `git diff --exit-code`
- data/ de un plugin (estado runtime, ej. clave AES de mail-server) NUNCA se empaqueta en el zip del catálogo (excluido explícitamente); theme/ (tema compañero, plugin-completeness opción B) SÍ se empaqueta y se instala vía POST /plugins/<slug>/install-theme

**Reutilización:** Compilador (esbuild + HOST_MODULES + resolución de externals) — REUTILIZABLE TAL CUAL: es infraestructura de bundling agnóstica al editor, no acopla a la implementación interna de Puck salvo por el SHAPE del objeto exportado (puckComponentDef/puckComponents). Un editor nuevo puede mantener build-plugin.js casi sin tocar si preserva ese shape de exportación, o adaptar solo el paso final que compone {...def, render}. Backend (rutas plugin-bundles.ts, plugins.ts /registry /active, estático /plugins) — REUTILIZABLE TAL CUAL, no conoce nada de Puck, sirve bytes JS/CSS y JSON. pluginBundleLoader.ts — ADAPTABLE: la lógica de fetch+Blob+import()+memoización+manejo de 404-vs-error es valiosa y debe conservarse (contiene ~10 fixes de carreras/cache-poisoning documentados en comentarios extensos, cada uno con un bug histórico real detrás); lo que cambia es SOLO la forma en que el resultado (mapa de bloques) se integra al config del editor nuevo — si el editor nuevo no usa el mismo objeto `Record<string,{fields,defaultProps,render}>` de Puck, este archivo necesita un adaptador de shape, no una reescritura. generate-puck-plugin-registry.js — ADAPTABLE, acoplado al nombre del import (`puckPluginComponents`) y a la detección regex de multi-block; portable si el editor nuevo mantiene el mismo contrato de exports en los plugins. withSharedBlockFields + AppearanceField/AnimationField/blockShell — REESCRIBIR bajo el motor del editor nuevo pero preservando el CONTRATO observable: mismos 3 campos (hide/anim/look), mismos defaultProps, mismo criterio de opt-out (`fields.hide` ya presente), mismo comportamiento display:contents→div-solo-si-hace-falta y las 2 capas separadas — esto es INVISIBLE para los plugins (ellos no lo importan, se aplica por fuera) pero ROMPE toda apariencia visual de las 31 páginas existentes si el editor nuevo no lo replica bit a bit. El de-facto API de bloque (fields text/number/radio/select/custom, category, defaultProps, sin render en el objeto de definición) es la parte más barata de portar (es solo un objeto plano) pero la más peligrosa de omitir: cualquier tipo de campo no soportado por el editor nuevo (aunque hoy nadie use array/object/textarea, Puck-core sí los expone y algún plugin de terceros fuera del catálogo auditado podría usarlos) rompe silenciosamente ese plugin.

**Riesgos:**
- themeSurfaces + prefijo .wjs-p-<slug>- es un LÍMITE DE SEGURIDAD (namespace ownership, previene que un plugin reclame clases de otro plugin o del chrome) — si el editor nuevo cambia CÓMO se renderizan las clases de un bloque de plugin (ej. las envuelve en un contenedor con su propia clase, o las procesa con CSS-in-JS con hashing) puede ROMPER la validación estructural de selectores sin que nadie lo note hasta que un tema intente aplicar tokens a FAQ y falle en silencio
- Solo 1 de 31 plugins (faq) usa themeSurfaces y solo 1 de 31 (mail-server) usa hooks — la cobertura de pruebas real de estos dos subsistemas en el catálogo es mínima; un editor nuevo que los migre mal puede pasar desapercibido en pruebas manuales hasta production
- El canal legacy de card-gallery (frontend.components[]+shortcodes[]+CardGalleryTool.js) es una superficie NO auditada en profundidad aquí — si sigue viva en algún renderer del core (no cubierto por graphify en esta pasada), migrar solo puckComponents dejaría ese canal roto sin que las pruebas de bloques Puck lo detecten
- pluginBundleLoader.ts documenta ~10 bugs de carrera/cache-poisoning ya corregidos (memoización de éxito-solamente, identity-guard en evicción, timeout de clasificación de 404, doble-registro de hooks bajo StrictMode/remount) — cada uno tiene una explicación extensa en comentario porque fue un incidente real; una reescritura que 'simplifique' el código sin leer esos comentarios reintroduce bugs ya cazados
- HOST_MODULES debe mantenerse sincronizado A MANO entre build-plugin.js (fuente de verdad de compilación) y pluginBundleLoader.ts (fuente de verdad de runtime) — no hay un test que falle automáticamente si diverge salvo el build-time throw en esbuild; agregar un HOST_MODULE nuevo sin tocar ambos lados rompe cualquier plugin que lo use, en producción, silenciosamente hasta el primer intento de carga
- El merge runtime de bloques ocurre en un useEffect DESPUÉS de hidratar — cualquier optimización del editor nuevo que intente renderizar bloques de plugin en el primer paint (SSR) para mejorar CLS/LCP debe re-verificar la hydration-safety (mismatch SSR/cliente) que este diseño evita deliberadamente
- La detección single-vs-multi-block es un REGEX sobre texto fuente (`/export\s+const\s+puckComponents\b/`), no un análisis AST — un plugin que oculte ese patrón detrás de una reexportación indirecta rompería la detección de forma sutil; el editor nuevo hereda esta fragilidad si reutiliza el mismo generador sin endurecerlo
- Ningún plugin del catálogo usa hoy los tipos de campo Puck array/object/textarea/external — si el editor nuevo decide NO soportarlos por 'no se usan', un plugin de terceros (fuera del marketplace oficial, instalado manualmente) que sí los use quedaría roto sin aviso
- El campo `look`/Appearance y `anim`/AnimSpec tienen lógica de seguridad embebida (clamps de duration/delay 100-3000ms) contra `_puck_data` hostil vía import WXR/API — replicar el campo sin replicar el clamp reabre ese vector
- marketplace/dist/*.zip y marketplace-index.json son DETERMINISTAS (fecha fija, sin timestamps) para que CI verifique con `git diff --exit-code` — cualquier cambio al pipeline de build (nuevo banner, nueva metadata) que introduzca un campo no-determinista rompe ese gate de CI sin relación aparente con el editor

**Contratos duros:**
- El objeto exportado por un bloque de plugin single-block DEBE tener la forma `{ category, fields, defaultProps }` SIN una clave `render` en `puckComponentDef` — el generador la añade componiendo `{...puckComponentDef, render: default}`; si el plugin incluye `render` ahí, el compose la pisa pero es una violación de contrato documentada explícitamente en 2 de los 4 ejemplos leídos
- El export multi-block DEBE llamarse literalmente `puckComponents` (el detector es una regex sobre ese nombre exacto) y ser `Record<string, {...def, render}>` ya compuesto por el propio plugin (no se compone después)
- HOST_MODULES en build-plugin.js y el objeto HOST_MODULES/imports en pluginBundleLoader.ts deben listar EXACTAMENTE las mismas 14 claves ('lib/api','lib/i18n','lib/plugin-hooks','lib/sanitize','contexts/ModalContext','contexts/I18nContext','contexts/ToastContext','contexts/AuthContext','components/MediaPickerModal','components/ui/StatCard','components/ui/PageHeader','components/ui/Card','components/ui/ActionCard') — divergencia = build roto o bloque que falla en runtime
- React/react-dom/react-dom-client/jsx-runtime/jsx-dev-runtime NUNCA deben bundlearse dentro de un bloque de plugin — deben seguir resolviendo a un singleton global inyectado por el host (hoy `globalThis.WordJS.React` etc.) o se rompe con 'Invalid Hook Call' en cualquier página con 2+ bloques de distintos plugins
- manifest.id debe ser IDÉNTICO al nombre de la carpeta del plugin — usado tanto para derivar el namespace CSS (.wjs-p-<slug>-) como para resolver rutas de bundle; un mismatch se rechaza explícitamente en 2 validadores distintos (build-marketplace.js y plugin-theme-surfaces.js)
- manifest.isolated debe ser `=== true` literal (no truthy) o el plugin no se empaqueta
- Un selector declarado bajo `themeSurfaces` DEBE estar compuesto EXCLUSIVAMENTE de clases que empiecen por `.wjs-p-<slug>-` (derivado del slug, no de una tabla) — prohibidos: id (#), atributo ([]), universal (*), pseudo (:), listas de selectores (,), y nombres de clase que no empiecen por el prefijo. Esto es un límite de seguridad (namespace ownership entre plugins), no solo una convención de estilo
- Las claves `children` de themeSurfaces no pueden colisionar con el set reservado del compilador de temas: hover, focus, active, disabled, before, after, placeholder, first, last, mobile, tablet, desktop, belowDesktop, motionOk, reducedMotion, dark
- El campo `type` de tokens declarados en themeSurfaces debe empezar por `--wjs-p-<slug>-`
- GET /api/v1/plugins/registry devuelve `{plugins:[...]}` (objeto), NO un array bare — cualquier consumidor nuevo debe desenvolver esa clave
- El bundle de un bloque de plugin se sirve SIN versión en la URL (`/api/v1/plugins/:slug/bundle?type=component`) — el cacheo correcto depende de ETag+no-cache, nunca de cache inmutable de largo plazo, porque el contenido cambia con cada rebuild del plugin bajo la MISMA URL
- El CSS de un bloque de plugin se sirve en la ruta ESTÁTICA `/plugins/<slug>/dist/component.bundle.css` (mapeada slug→carpeta cuando difieren), no en la ruta API `/bundle/css` — un editor nuevo que solo mire la API rompería los estilos de bloques con CSS externo
- Todo bloque de plugin que haga fetch a su propio backend debe tratar CUALQUIER respuesta no-ok (incluido 404 = plugin inactivo) como degradación silenciosa, nunca como excepción no capturada — es el contrato implícito que mantiene páginas públicas renderizables cuando un plugin se desactiva
- El primer render de un bloque de plugin en el cliente (hidratación) DEBE coincidir con el HTML del servidor — los bloques de plugin NO tienen paso de datos SSR, así que cualquier fetch de datos debe ocurrir estrictamente después de montar (useEffect), nunca durante el render inicial, o se rompe la hidratación
- withSharedBlockFields NUNCA debe re-envolver un componente que ya declare `fields.hide` — es el único mecanismo de opt-out y algún bloque futuro podría depender de él
- El objeto de config identidad-estable: cualquier editor nuevo que re-genere el objeto de configuración de bloques en cada render (en vez de memoizarlo) fuerza un remount completo del árbol de edición — contrato de rendimiento no negociable heredado de cómo Puck trata la identidad de `config`
- Un tema (según la regla ya establecida en memoria del proyecto) JAMÁS envía JS — los bloques de plugin, en cambio, SÍ son JS arbitrario del propio plugin; el editor nuevo no debe confundir ambos límites de confianza (tema = solo tokens/CSS; plugin = código ejecutable aislado por HOST_MODULES/externals)
