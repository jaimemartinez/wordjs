# WordJS Mail Server Plugin

The Mail Server is a powerful plugin (version **3.0.3**; source in `marketplace/plugins/mail-server`, installed to `backend/plugins/mail-server`) that adds full MTA capabilities to WordJS: an inbound SMTP server, direct-to-MX outbound delivery, DKIM/SPF/DNSBL/Bayesian security, and a scheduled + retry delivery queue.

> **Optional, isolated, per-capability grants — no trust tier.** The Mail Server is **not** required to run WordJS. Like every isolated plugin it runs in a **separate OS process** (`child_process.fork` of `plugin-worker.js`, not a `worker_threads` isolate) and reaches core only through the `wordjs` capability bridge, RPC'd over IPC and permission-checked on the host. There is **no "trusted" tier** — no plugin bypasses the sandbox. The Mail Server works purely from the capabilities its `manifest.json` **requests** and an admin **grants** (default-deny, Android-style). Outbound sockets (DNS + TCP to remote MX servers on port 25) require the **`network`** grant, and so does the inbound SMTP listener where the platform lets an isolated plugin listen at all (on Linux the plugin sandbox does not, grant or no grant; see Inbound SMTP below) — without it `net`/`tls`/`dns` are blocked inside the isolate and delivery degrades gracefully. Its secrets (DKIM private key, relay creds) live in the plugin's **own** `wjp_mail_server_secrets` table, not in protected core options; becoming the host-wide mail provider requires the **`email:provider`** grant, and having WordJS listen on port 25 for it the exclusive **`smtp:inbound`** grant. Its manifest also requests **`browser:script`**: it ships an admin page (the Email Center, `/admin/plugin/emails`) and a frontend **hooks** file (`client/UserFormExtension.tsx`, the "Professional Mail Account" toggle the core user form renders through the `user_form_before_email` hook), and that compiled code runs in the admin's browser with the viewer's session. Even though it is a first-party plugin, it is **not** privileged: it goes through the same grant path as any plugin. Activating it (`POST /plugins/mail-server/activate`, admin-only) shows the admin the capabilities the manifest requests and grants exactly that declared set — but only while the plugin holds no grants an administrator decided (no record, or an empty one with no administrator decision recorded), so a per-permission revoke in `/admin/plugins` survives a re-activation, a revoke of every grant included. (Plugins that were *already active* when the default-deny model was introduced were grandfathered by the non-breaking boot backfill.) Activate it only if you want a self-hosted mail server.

## Features

*   **Internal Routing:** Mail addressed to a colleague's corporate mailbox on the mail domain (an account with the admin-granted `professional_mailbox` flag and an on-domain address) is written straight to the database (the recipient's inbox copy) without leaving the server; mail to a local user's personal address on another domain is delivered out to that provider.
*   **Inbound SMTP — `smtp:inbound` (recommended):** no platform's plugin sandbox lets an isolated plugin open a listening socket (Linux seccomp, macOS Seatbelt, Windows AppContainer without `internetClientServer`). Grant the Mail Server the exclusive **Receive internet email (port 25)** permission (`smtp:inbound`) and **WordJS itself** listens on port 25 (falling back to 2525 with the reason when it cannot bind 25) and hands each SMTP step to the plugin — DNSBL at connect, SPF at MAIL FROM, the site blocklist at RCPT TO, delivery at DATA — so inbound mail works on every platform with the sandbox intact. Only one plugin can hold this permission. The admin console shows which listener is active (`inbound_mode`: `host` or `plugin`).
*   **Inbound SMTP — plugin's own listener (fallback):** without that grant the plugin tries its own `smtp-server` listener on port `25` by default — the port the world actually delivers mail to (configurable via `smtp_listen_port`). The plugin **probes port 25 before binding**: if it can't be bound it falls back to `2525` and records a **degraded** status with the reason the error identifies. `EADDRINUSE` — another MTA is already on 25. `EACCES` — the process may not bind a port below `net.ipv4.ip_unprivileged_port_start` (1024 by default); this only happens when the plugin runs **without** the Linux sandbox, and the fixes are a firewall redirect 25 → 2525 or lowering that sysctl to 25 (which lets every unprivileged process bind 25-1023) — never `setcap` on node or capabilities on the service. `EPERM` — on Linux with the plugin sandbox active (the default), its seccomp filter refuses `bind`/`listen` to every isolated plugin on **every** port, network grant or not: inbound SMTP cannot listen there at all (the fallback to 2525 is refused the same way), and no port, sysctl or capability setting changes that; sending and local mail are unaffected. The status is surfaced in `GET /settings` as `inbound_bound_port` / `inbound_degraded` / `inbound_reason` / `inbound_ok` instead of inbound being lost silently. Hardened against abuse: 25 MB per-message cap, `maxClients: 50`, 60s socket timeout.
*   **Outbound Delivery:** **Direct-to-MX** by default — resolves the recipient domain's MX records and connects on port 25 (STARTTLS when offered). Each MX host is resolved + validated to a **public** IP, and the connection is **pinned to that validated IP** (the real MX hostname is kept as the TLS `servername` for cert/SNI) so there is no second, attacker-controlled DNS lookup at connect time — closing the DNS-rebinding/TOCTOU window where a hostile recipient domain could aim delivery at loopback / RFC1918 / `169.254.169.254` cloud metadata / CGNAT / IPv6 ULA (the IP check fails closed on an unparseable address). The STARTTLS certificate is verified against that MX hostname; only when the verification itself fails (a self-signed certificate or chain root, a leaf whose issuer is neither sent nor trusted, an expired certificate, or a hostname mismatch — never another TLS, network or SMTP error) is that one host retried with verification off, still using STARTTLS when the host offers it (opportunistic encryption — like the first attempt, it does not require TLS), and the downgrade is logged as `[MailServer][TLS]`. An MX that **refuses** STARTTLS with an SMTP reply (e.g. `454 4.7.0 TLS not available` from a server with no certificate) gets the message in plaintext on a second connection, logged as `[MailServer][TLS] … refused STARTTLS` — opportunistic TLS as every MTA does it, and the same outcome as a server that never advertised STARTTLS; a handshake that starts and then fails is still not downgraded. If an SMTP **relay/smarthost** is configured (`mail_server`; credentials are optional), that path is used instead, and it is the **only** outbound path: when the relay does not answer, external mail stays in the retry queue and the console shows **Relay unavailable: <reason>** (server health, the Configuration tab and the Test tab). It is never rerouted direct-to-MX. The plugin's own public-only pin does not apply to the relay, because it is an **operator-set, admin-only** value. The WordJS plugin sandbox still lets plugins reach **public addresses only**, so a relay on a **private** address (a LAN smarthost such as `192.168.1.20:587`) also needs an administrator to approve that exact destination: **Configuration → Relay / smarthost → Sandbox access → Allow `<host>:<port>`**, which calls `POST /api/v1/plugins/mail-server/private-egress`. The approval covers that one host on that one port and nothing else on the private network. Link-local addresses (including `169.254.169.254`), unspecified and multicast addresses cannot be approved. Without the approval the relay status says the sandbox blocked it.
*   **Inbound Security:** **DNSBL** (Spamhaus zen) at connect and real **SPF** evaluation of the connecting IP against the `MAIL FROM` domain are both **default-ON**. Their failure modes differ deliberately: **DNSBL fails open** — Spamhaus zen refuses queries from public/cloud resolvers, so a lookup *error* is the common case and rejecting on it would blackhole all inbound mail; only a **positive listing** rejects (with `554`), and SPF + the Bayesian filter still apply. The listing is read from the blocklist's **TXT** record for the reversed IPv4 through the host DNS bridge (the bridge never returns the `127.0.0.x` A answer a listing also carries); an error record such as Spamhaus' open-resolver refusal is treated as *no verdict*, and IPv6 senders are not checked. **SPF fails closed** for external senders — a temporary evaluation error (`temperror`, including an unexpected resolver throw) **defers with `451`** so the sender retries rather than admitting an unverified IP, and an explicit SPF `fail` (`-all`) **rejects with `550`**. `softfail` (`~all` — what Gmail/Google/Microsoft publish; RFC 7208 §8.5 says it must not be rejected on its own) and `permerror` (a malformed / over-budget policy, §8.6) are **accepted and tagged**, never refused: the verdict is recorded as an RFC 7208 `Received-SPF` header and persisted on the message row (`received_spf`). `mail_security_spf_reject='0'` turns **every** SPF-driven refusal — both the `550` and the `451` — into tag-only; the one deferral it cannot override is when the option lookup itself fails, in which case the message is still deferred with `451` (fail closed, retryable). Loopback connections (`127.0.0.1`, `::1`, and the IPv4-mapped `::ffff:127.0.0.1` that the dual-stack listener reports) are trusted and bypass both checks. The inbound listener is an unauthenticated MTA — the SMTP `AUTH` command is disabled (`disabledCommands: ['AUTH']`), so there are no authenticated inbound sessions; the code's trust of `session.user` is a forward-compatibility guard only, not a supported submission path. A **Bayesian spam filter** classifies every inbound message at delivery and files a positive into the **Spam** folder (the `is_spam` flag, which is a different folder from Trash); it learns only from an explicit user train action, never from its own verdict. It needs evidence before it files anything: at least 5 trained messages in each class, words it has actually seen, and a clear margin (9:1 odds) — otherwise the message stays in the inbox (an untrained or barely trained filter used to tie and break the tie towards Spam).
*   **Received HTML:** inbound HTML is rebuilt through a strict allowlist before it is stored. Inline `style` survives only as a rebuilt list of layout/typography properties with plain values (colours, fonts, spacing, borders, sizes, alignment) — no `url()`, `expression()`, CSS escapes, comments, at-rules or entities, and no positioning — along with presentational table attributes, so newsletters keep their look. The reader renders the result in a script-less sandboxed frame.
*   **Forwarding with attachments:** forwarding a message carries its original files. The composer names each one by attachment id; the server honours an id only if the user may read the message it belongs to and copies the stored file into the new message.
*   **DKIM and DMARC (inbound):** every message from an external session is checked after DATA (`lib/mail-auth.js`, `node:crypto` plus the host DNS bridge — no extra permission beyond `network`). **DKIM** signatures are verified per RFC 6376: `rsa-sha256` and `ed25519-sha256` (RFC 8463), `simple`/`relaxed` canonicalization, `l=` and `x=`; `rsa-sha1` and RSA keys under 1024 bits are not accepted (RFC 8301), a signature must cover `From`, and at most 5 signatures are checked. **DMARC** (RFC 7489) looks up `_dmarc.<From domain>`, then the organizational domain, and passes when SPF passed for an aligned envelope domain or a DKIM signature passed for an aligned `d=` (`adkim`/`aspf` relaxed or strict). On a failure the policy acts — `p=reject` refuses with `550 5.7.1`, `p=quarantine` files every copy in **Spam** (overriding the mailbox's own rules) and forwards nothing, `p=none` only records — with `sp=` for subdomains found at the organizational record and `pct=` sampling (outside it, reject becomes quarantine and quarantine becomes none). A DNS failure (`temperror`) never rejects. The verdict is stored on the message row as an RFC 8601 `Authentication-Results` value (`auth_results`), and the reading pane shows it as badges. A valid DKIM signature of the site's own mail domain also satisfies the local-From check below. `mail_security_dmarc_enabled='0'` turns the whole check off.
*   **Local-domain From check:** an external session whose header `From` or envelope sender is on the mail domain is refused with `550 5.7.1` unless SPF passed for that domain or a valid DKIM signature of it covers the message. Inbound copies go to the SMTP envelope recipients accepted at `RCPT TO`; the `To`/`Cc` headers are display only.
*   **Deliverability:** **DKIM** signing (generate a keypair in-app), a DNS-records helper that emits the DKIM/SPF/DMARC/PTR records an operator must publish, and a **live DNS check** (`GET /security/dns-check`) that resolves MX/A/SPF/DMARC/DKIM and verifies the published DKIM `p=` key matches the generated one — when everything resolves it sets the generic `mail_delivery_ready` option that core features (e.g. password recovery) gate on. With a relay configured, the relay decides instead: `mail_delivery_ready` is `1` while the relay answers its check and `0` while it does not, and the DNS check leaves it alone (the relay, not your domain's records, is what delivers).
*   **Reliability:** scheduled send + an outbound **retry queue** with exponential backoff and sender bounce notifications.
*   **Real-time Alerts:** integrates with the Notification System to alert users of new inbound/internal mail instantly.
*   **Aliases and distribution lists:** `info@`, `sales@` or a whole-team address on the mail domain that deliver to one or more local mailboxes and/or forward to external addresses (admin console → Aliases). An alias may name another alias (one level). It can never shadow a real mailbox (`409`).
*   **Server-side filters and blocked senders (per user):** rules that run on the server as mail arrives — conditions on From / To-Cc / Subject / Body / anywhere (contains, doesn't contain, is, starts with, ends with; all or any) and actions (apply one of your labels, mark read, star, skip the inbox, delete, send to spam, never send to spam, stop processing). A blocked sender (an address or a whole `@domain`) goes to Spam, never silently dropped. Both apply to inbound SMTP and internal mail alike.
*   **Auto-forward (per user):** forward a copy of incoming mail to an external address, keeping the WordJS copy in the inbox or archiving it (never deleting it). Forwards are sent *from* the forwarding address (so DKIM/SPF align) with the original sender in `Reply-To`, tagged `X-WordJS-Forwarded` so a forward is never forwarded again, spam is never forwarded, and every forward counts against the outbound rate limit. The administrator can switch external forwarding off for the whole server (`mail_forwarding_allowed`).
*   **Quotas:** a site default (`mail_quota_default_mb`, `0` = unlimited) and a per-mailbox override (admin console → Mailboxes). A full mailbox refuses inbound SMTP with a temporary `452 4.2.2` (the sender retries) and fails internal mail to it as a permanent failure the sender sees; each user sees their usage in the webmail sidebar (`GET /quota`).
*   **Recipients are checked at `RCPT TO`:** an address on the mail domain that is neither a mailbox, an alias nor covered by catch-all is refused with `550 5.1.1` (the sending MTA bounces it to the sender), and any other domain with `550 5.7.1 Relaying denied` — never accepted and silently dropped. A lookup failure answers a temporary `451`.
*   **Site sender lists:** `mail_blocked_senders` is refused at the SMTP envelope (`550 5.7.1`, at `RCPT TO`); `mail_allowed_senders` is never filed as spam by the classifier. One address or `@domain` per line.
*   **Server console (administrators):** traffic for the last 14 days, storage, server health, recent activity; every mailbox with its usage and quota; aliases; the outbound **queue** (scheduled sends, retries and failures — retry now, or stop a message: a scheduled send goes back to its author's drafts, a retrying one is marked failed); policies; SMTP/relay/DKIM configuration; DNS records with live verification; a delivery test.
*   **Webmail:** responsive from phone to wide desktop (three columns, an icon rail, or a drawer with a full-screen reader and composer, chosen from the space the page actually has), recipient chips with autocomplete, rich text, drag-and-drop attachments, reply / reply all / forward, scheduled send presets, reply templates, collapsible conversations, remote images held back until the reader asks (no tracking pixels on open), printing, "filter messages like this", block sender, keyboard shortcuts (`?` lists them) and Spanish/English following the admin language.

## Configuration

Settings are managed via the Admin Panel -> **Email Center** -> **Mail server** (the server icon; administrators only) and persisted as core options. An administrator without a mailbox of their own lands straight on the console.

*   **From identity:** `mail_from_email`, `mail_from_name`.
*   **SMTP listen port:** `smtp_listen_port` (default `25`; automatic fallback to `2525` when 25 can't be bound, reported as a degraded status — except under the Linux plugin sandbox, which refuses a listening socket on any port; see Inbound SMTP above). With `smtp:inbound`, WordJS opens any port the manifest declares (`25`) or any unprivileged port (`1024` and up), so a port-mapped setup can use `2526`. If WordJS refuses the configured port, the plugin listens on `25` instead and the console shows which port was refused and why. The manifest also declares `claimPorts: [25]`, so when a distro's preinstalled MTA (Postfix/Exim/Sendmail) is squatting the port, the admin UI can show what is occupying it and — after explicit confirmation — permanently disable that known service and reload the plugin (host-side only, admin routes; never reachable from a plugin, and unknown occupants are only reported, never touched).
*   **Trusted proxy IPs:** `smtp_proxy_ips` — comma/space-separated IPs allowed to send the **PROXY protocol (v1)** header (nginx `stream` with `proxy_protocol on;`, HAProxy `send-proxy`), so the real client IP reaches DNSBL/SPF/logging when inbound mail arrives through a TCP proxy. Only exact IPs are honored, never a blanket trust.
*   **Catch-All:** `smtp_catch_all` — accept all incoming mail for the domain even when the user doesn't exist.
*   **HELO host:** `mail_helo_host` — the name announced in EHLO; **must** match the sending IP's reverse DNS (PTR) or Gmail/Outlook will reject or spam your mail.
*   **Relay (optional):** `mail_server` / `mail_port` / `mail_user` / `mail_pass` / `mail_secure` — configure a smarthost instead of direct MX. Only `mail_server` is required; without `mail_user`/`mail_pass` the plugin connects without authenticating (for a smarthost that relays for your network by address). `GET /settings` returns `relay_status` (`configured`, `ok`, `host`, `port`, `error`, `sandboxBlocked`, `checkedAt`); a failed relay is re-checked at most once a minute when mail is waiting. The relay credentials (`mail_user`/`mail_pass`) are **secrets**: they are stored encrypted in the plugin's own secrets table, not as core options (see *Secrets at rest* below). `mail_relay_require_tls` (default `'1'`) forces STARTTLS on the non-implicit-TLS relay path so an on-path attacker can't strip TLS and capture the relay creds; an operator with a TLS-less **internal** smarthost can opt out with `mail_relay_require_tls='0'`. `mail_secure='1'` (port 465) is implicit TLS and not subject to this.
*   **Security toggles:** `mail_security_dnsbl_enabled`, `mail_security_spf_enabled`, `mail_security_spf_reject`, `mail_security_dmarc_enabled` — all **default ON** (`'1'`); only an explicit `'0'` disables them. Plus DKIM (`mail_security_dkim_domain`, `mail_security_dkim_selector`, plus the secret `mail_security_dkim_private_key`, which is never returned by the settings API).

### Secrets at rest

The DKIM private key (`mail_security_dkim_private_key`) and the relay SMTP credentials (`mail_user`/`mail_pass`) are **not** stored as core options. They live in the plugin's own `wjp_mail_server_secrets` table, **encrypted at rest with AES-256-GCM**. The root key is a 32-byte random value persisted once to `backend/plugins/mail-server/data/.mailenc` (written `0600` where the OS honors mode — `chmod` is re-applied after write; a no-op on Windows) and HKDF-stretched to the per-use AES key. Pre-encryption plaintext rows stay readable (backward compatible), and ciphertext is never returned to callers.

> **Operations note — decrypt failure.** If a stored secret carries the `enc:v1:` marker but its GCM auth tag fails to verify, the plugin logs a clear, actionable operator error and treats the secret as **unset** (returns `''`). This almost always means the `.mailenc` root key was **lost, rotated, or regenerated** (e.g. a DB restore that omitted the key file), not tampering. The plaintext is unrecoverable, so the affected DKIM key / relay credential must be **re-entered** in the mail server settings.

## Delivery model

A single `send` produces, in order:
1.  **A "Sent" copy** in the sender's mailbox (the source of truth). On retries this record is reused, not duplicated.
2.  **Local inbox copies** for recipients that resolve to a local user holding an **active corporate mailbox on the mail domain** — the same predicate the inbound listener uses: the admin-granted `professional_mailbox` flag **plus** an account address actually on the mail domain (see *Email Center visibility* below). Each such recipient also gets a notification (self-sends skip the extra inbox copy and notification, since the Sent record already represents the message). A local account without that flag, or a user's personal address on another domain, is **not** captured locally — it is delivered externally like any other address. Retry passes skip this step; only the still-failed external recipients are re-attempted.
3.  **External delivery** for the rest — direct-to-MX (or the configured relay).

The outcome of a delivery is reported back to the caller as `{ success, delivered, failed }`. Note that by default `POST /send` does **not** deliver synchronously: unless `scheduledAt` is given, the message is held in the outbox for an **undo window** (`mail_undo_send_seconds`, default `10`, clamped to 0–60; editable under Settings) and the endpoint answers `200 { success: true, queued: true, undoSeconds, id, message: 'Sending…' }`. The 15-second background queue then dispatches it; a delivery failure at that point surfaces as retry state / a bounce notification (see below), `POST /emails/:id/retry` re-attempts a `failed`/`retry` message immediately, and `POST /emails/:id/unsend` cancels a message still inside its undo window (or a scheduled send) and turns it back into a draft (`409` once it has been handed off). Only with `mail_undo_send_seconds` set to `0` is delivery synchronous — and then `/send` returns `207` (`success: false`, `delivered`, `failed`) on partial or total external failure rather than silently "succeeding".

### Scheduled send & retry queue
*   A background timer that ticks every **15 seconds** (it was 60 s; the shorter tick is what makes the ~10 s **undo-send** window feel immediate, since a message sits in the outbox until the next tick dispatches it) processes two queues:
    *   **Scheduled:** rows with `scheduled_at <= now` are sent. `scheduled_at` is stored as an **ISO/UTC** timestamp and compared against an ISO bind parameter (`scheduled_at <= ?`) — not SQLite's localtime `datetime('now')` — so timing is correct on any driver.
    *   **Retry:** outbound rows in `delivery_status = 'retry'` whose `next_attempt_at` (also ISO) is due are re-attempted against only the still-failed recipients.
*   **Backoff & give-up:** temporary failures (4xx / network) schedule the next attempt at `attempt²` minutes (cap ~6h) up to `MAX_DELIVERY_ATTEMPTS` (5); permanent failures (5xx) never retry. On final failure the sender gets a **bounce notification**.

### Outbound rate limiting
Per-user, per-rolling-hour caps guard against an authenticated account blasting DKIM-signed spam from your IP: max 50 recipients per message, 100 messages/hour, 500 recipients/hour. Header-bound fields (subject, from-name) are CR/LF-stripped to prevent header injection, and recipient addresses are validated (length, single `@`).

## Developer API

Other plugins send mail through the bridge. **Sending** is the everyday path: `wordjs.mail(msg)` is an **allowlisted bridge call** (in `ALLOWED_BRIDGE_METHODS`) available to any plugin — it requires the `email`/`admin` capability (declared in the manifest **and** granted) and RPCs to the host, which forwards to whatever plugin is the registered mail provider. **Becoming** the host-wide mail provider is the privileged path: only the Mail Server does that, via `wordjs.provideMail(sendMail)` (the `register-mail-provider` IPC kind). That requires the admin-granted **`email:provider`** capability — there is **no trusted bypass**; the grant is re-checked both at the `register-mail-provider` IPC handler and inside `provideMail` itself, so a plugin without it cannot reach it via a generic `call`.

A plugin sends with `await wordjs.mail({...})`. The call is an RPC, so await it; it throws `Mail server not available` when no provider is registered (the Mail Server inactive, say) and a `Security Block` without the `email:admin` grant:

```javascript
// manifest.json permissions: { "scope": "email", "access": "admin", "reason": "Sends booking confirmations" }
// (plus express:register_route for the route itself)
exports.init = function (wordjs) {
    wordjs.http.route('post', '/notify', { auth: true, admin: true }, async (req, res) => {
        try {
            const result = await wordjs.mail({
                to: 'user@example.com',          // string or array
                subject: 'Hello',
                text: 'Sent from another plugin!',
                html: '<p>Sent from another plugin!</p>'
            });
            res.json({ ok: true, result });
        } catch (e) {
            res.status(503).json({ ok: false, error: e.message });
        }
    });
};
```

The host side keeps the provider in a host global (`wordjs_send_mail`, see `backend/src/core/mail-provider.ts`); that global exists only in the host process, and plugin code cannot read `global` anyway (the AST scanner refuses it, `plugins.md` §7.2), so always go through `wordjs.mail`.

The Mail Server also registers an **`email` notification transport**, so any `notify({ transports: ['email'] })` is delivered by mail.

### HTTP API (authenticated)

All routes are mounted by the host under `/api/v1/plugin/mail-server/*` (every isolated plugin is namespaced under `/api/v1/plugin/<slug>` — no route-hijack/`absolute` bypass). Highlights:

| `GET /emails/search`, `GET /users/search` | Search mail / local users. |

```json
}
```

**Access control:** every route above except `GET /mailbox` and the admin ones carries a `mailbox: true` gate, so being authenticated is not enough — the caller needs an **active corporate mailbox**, or the administrator role, or the route answers `403` with `code: "mail_no_corporate_mailbox"`. The gate lives once in the plugin's own `route()` helper rather than in ~30 handlers, and the option-less `route(method, sub, handler)` form means `{ auth: true, mailbox: true }`, so a new route cannot default to public. On top of that, `POST /classification/train` is **owner-scoped** — only the email's sender/recipient or an administrator may train on it (returns `403` otherwise). Training also re-files the message: `spam` flags it into the Spam folder (recording who flagged it, and un-archiving it), and `ham` clears the spam flag and restores it from Trash if it was there — it never trashes anything. So one user can't poison the shared Bayes filter or re-file another user's message by id. Attachment downloads encode the (attacker-controlled) filename safely into `Content-Disposition` — an ASCII quoted-string fallback with CR/LF + quotes stripped, plus the real name via RFC 5987 `filename*=UTF-8''`. And the plugin subtree goes through the host's double-submit CSRF gate like every other cookie-authenticated write: a `POST`/`PUT`/`DELETE` above that authenticates with the `wordjs_token` cookie must also send `X-CSRF-Token` equal to its `wjs_csrf` cookie, or it answers `403` with `code: "rest_csrf_token"` before the handler runs. A caller authenticating with `Authorization: Bearer …` is exempt — it carries no ambient cookie to ride.

## Notes
*   **Localhost / dotless domains**: `admin@localhost` and similar are accepted for internal testing.
*   **The mail domain** is the DKIM domain when one is set, else the site's host. On a site reached by IP, `localhost` or a LAN name, mailboxes become `@localhost` (or similar) and no other server can deliver to them. The console warns about it (server health and the Configuration tab, `mail_domain` / `mail_domain_public` in `GET /settings`), and so does the server log at startup. Set the site address to a real domain, or set the DKIM domain.
*   **Email Center visibility**: the plugin registers its admin menu (via `wordjs.adminMenu.add`) with `requiresProfessionalMailbox: true`, so core (`GET /plugins/menus`) **hides the Email Center** from users with no active corporate mailbox — they have no WordJS inbox, so the page would be an empty shell. Administrators always keep it, which is why the route gate lets them through too: a stricter rule there would show an admin a menu entry whose page only 403s. That grant is **not** derived from the account's email domain: it is the explicit `user_meta.professional_mailbox` flag (`backend/src/core/mailbox.ts`), writable only by a caller holding `edit_users` (Users → edit user → Professional Mail Account) and listed in `User.update`'s protected-meta set so it can never be mass-assigned through the generic `meta` bag. Schema migration `0006_professional_mailbox_flag` performed that conversion on existing installs, granting the flag only to accounts that could already have set it themselves (administrators and `edit_users` holders) and naming every other on-domain account in the `professional_mailbox_migration_pending` option for the operator to re-enable by hand. The flag is slug/href-agnostic, so any mail plugin gets the same treatment (it isn't tied specifically to the mail-server plugin).
*   **Storage**: mail lives in the plugin's own prefixed tables `wjp_mail_server_received_emails` / `wjp_mail_server_email_attachments` (plus `wjp_mail_server_labels`, `wjp_mail_server_email_labels`, `wjp_mail_server_user_prefs`, `wjp_mail_server_aliases`, `wjp_mail_server_mailboxes` and `wjp_mail_server_secrets`) via the bridge `wordjs.db`. Because the plugin can only write inside its own directory, attachments are stored under `backend/plugins/mail-server/data/attachments` and the Bayesian model persists to `backend/plugins/mail-server/data/bayes.json`.
*   **Logging**: verbose, tagged `[MailServer]`, for tracing delivery paths.
