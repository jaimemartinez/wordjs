# Security Policy

> **Posture (be realistic).** WordJS is **pre-production** and primarily solo-maintained. The defenses
> below are real and tested, but the project has **not** had an independent security audit — one is
> **recommended before any production deployment**. Operators **must** complete the hardening steps in
> the checklist (rotate `jwtSecret` / `gatewaySecret` / `db.password`, set a strong `gatewaySecret`)
> before exposing an instance to the internet. See [`documentation/security.md`](documentation/security.md)
> for the deeper defenses reference.

## 🛡️ Security Features

WordJS is built with a "Security First" architecture.

### Active Defenses
- **Rate Limiting**: Per-IP brute-force protection on login and API endpoints (backend).
- **Per-Account Login Lockout**: A single account is locked for 15 minutes after 10 consecutive failed logins — this throttles a distributed/botnet attack that defeats the per-IP limiter.
- **Helmet Headers**: HSTS (`max-age=31536000; includeSubDomains`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy`, `Cross-Origin-Opener-Policy` — on both the gateway and the backend. Note that the shipped Helmet (`^8`) emits `X-XSS-Protection: 0`, which **disables** the legacy browser XSS auditor rather than enabling it, so it is not an XSS control; the server-side sanitizer is. (The **frontend ships a real Content Security Policy** on every route, and the gateway emits its own Helmet CSP — `gateway/src/security-headers.js` — on the responses it generates itself; see **Content Security Policy** below.)
- **Content Security Policy**: The **frontend** serves a CSP on every route (`frontend/next.config.ts` `headers()`): `default-src 'self'`, `script-src 'self' 'unsafe-inline' blob: https:`, `style-src 'self' 'unsafe-inline' https:`, `img-src 'self' data: blob: https:`, `font-src 'self' data: https:`, `connect-src 'self' https: http: ws: wss:`, `worker-src 'self' blob:`, `frame-src 'self'` plus the embed hosts derived from `contracts/visual-contract.v1.json`, `frame-ancestors 'self'`, `object-src 'none'`, `base-uri 'self'` — and the structural three (`frame-ancestors`, `object-src`, `base-uri`) are what this header is really worth: cross-origin clickjacking, object injection, base-tag hijacking. **`'unsafe-eval'` is gone from every production surface that sets a policy** — frontend, gateway (`gateway/src/security-headers.js`) and backend (`backend/src/index.ts`). The frontend keeps it in *development* only, because React's development build calls `eval()` to reconstruct component stacks and logs on every page without it; the gateway and backend policies are static and carry it in no environment. It existed for the retired Puck editor, and the evidence for dropping it is the real production client build: zero `eval(` and zero `new Function(` (the only two `Function("` occurrences are core-js's and decimal.js's global-object fallbacks, which short-circuit on `globalThis`/`self` and are unreachable in a browser), no WebAssembly, and clean shipped plugin admin bundles. Shape tests pin the absence on all three surfaces (`frontend/src/lib/__tests__/embedHostsCsp.test.ts`, `gateway/test/security-headers.test.js`, `backend/src/tests/public-surface-hardening.test.ts`). On the backend the only HTML that origin serves is the Swagger UI page at `${prefix}/docs`, and `swagger-ui-express` emits **all three** of its scripts as **external** tags (`./swagger-ui-bundle.js`, `./swagger-ui-standalone-preset.js`, and the bootstrap itself as `./swagger-ui-init.js`); the page's only inline element is the `customCss` `<style>` block, which `style-src` already covers — so `script-src 'unsafe-inline'` on the backend is a **holdover, not a requirement**, and narrowing it is a follow-up. Nothing on that surface builds a script from a string. What is still permissive is under Known Limitations; narrowing `https:` means proxying the admin-entered Matomo origin same-origin (or emitting the header per request) and only then listing explicit origins — see [`documentation/security.md`](documentation/security.md) §10.
- **IO Guard**: Recursive filesystem locks to prevent unauthorized plugin access outside their directory.
- **Allowlisted Plugin Asset Serving**: `/plugins/<slug>/…` publishes only `public/**` with a servable extension plus three fixed host-known files; source, `data/`, `.map` and anything a plugin writes at runtime return `404`. The whole `public/` subtree — and `dist/`, the build output the unauthenticated bundle routes serve — is simultaneously **unwritable** by the plugin, and both rules are derived from one declaration in `core/io-guard.ts`. Previously the entire plugin tree was served raw while a plugin could write its own directory with no grant — a write-then-fetch exfiltration channel that no socket-level control (the `network` grant, the egress guard or the native network boundary) can see, and one that leaked a stock install's `data/` directories with no malicious plugin at all.
- **Zip Slip Protection**: Every entry in an uploaded plugin or theme archive has its resolved path verified to stay inside the target directory before extraction.
- **Marketplace Install Integrity**: One-click installs from the admin Marketplace tab (`backend/src/routes/marketplace.ts`) fetch catalog zips server-side (https-only, size-capped, strict filename shape), verify them **sha256** against the catalog entry, and hand off to the **same** guarded zip-install pipeline as manual uploads (zip-bomb budget, Zip Slip, slug validation, manifest + AST scan) — the marketplace adds no separate install surface beyond the catalog fetch.
- **SVG Sanitization**: Strips malicious scripts from vector images.
- **Identity Isolation**: mTLS authentication between Gateway, Backend, and Services. The **gateway is the cluster CA** (`gateway/src/cluster-ca.js`); each service holds a per-node certificate (`CN` in `{backend, frontend}`) signed by that CA, and the internal control plane (`POST /register`, health checks) requires a valid client cert. The gatewaySecret is an additional shared-header secret on top of the mTLS channel.
- **Token-Bound Node Enrollment** (separate mode): when the three services run on **different machines**, a new node bootstraps its mTLS identity with a **single-use, role-bound, TTL-limited join token** minted on the gateway (`node scripts/cluster.js token <backend|frontend>`). `node scripts/node-join.js` sends a CSR to a **dedicated token-enrollment listener** (default port `3101`, a separate HTTPS listener that does **not** request a client cert; the strict mTLS `/register` listener is unchanged); the gateway validates the token, **forces `CN` = the token's role** (the CSR subject is ignored), pins the cert's **SAN** to the host the token pinned (or, for an unpinned token, to the address the node is connecting from — so a token holder cannot mint a cert that impersonates the gateway), signs the cert, and returns it with the cluster CA certificate (never the CA key). `node-join` verifies the CA fingerprint (`--ca-hash`, a MITM guard) before trusting the response **when that flag is passed** — the enrol call itself runs with TLS verification off, since the node has no trust anchor yet, so an enrolment without `--ca-hash` is plain trust-on-first-use; the command `cluster.js token` prints always includes it. The token is burned after first use. See [`documentation/separate-mode.md`](documentation/separate-mode.md).
- **One-Time Install Token**: The pre-install setup endpoints (`POST /setup/install`, `POST /setup/test-db`) are the only two paths exempt from both halves of the CSRF check, and are instead gated by a one-time token printed to the server console (and mirrored to a `0600` file in the data dir; overridable via `WORDJS_INSTALL_TOKEN`, ≥16 chars), compared in constant time and cleared once installed — preventing pre-install takeover. The console prints it as a `…/install#token=…` **URL fragment**: a fragment is never transmitted to the server, so unlike a `?token=` query it cannot land in access or proxy logs, nor in the `Referer` of a sub-resource, and the install page scrubs it from the address bar on arrival (the query form is still accepted as a compatibility ramp, and scrubbed just as aggressively).
- **Import Identifier Allowlist**: The JSON `custom_tables` import validates every table and column name against a strict simple-identifier regex and refuses core tables + `sqlite_*` reserved tables before any SQL interpolation.

### Authentication & Transport
- **JWT Signing**: The signing secret never falls back to a public constant. When none is configured, a per-process ephemeral random secret is used (issued tokens stop working after a restart). Configure a real secret via setup for production.
- **Algorithm Pinning**: `jwt.verify` is pinned to `HS256`.
- **Stateless-JWT Revocation**: Logout and password change stamp a per-user security epoch (`token_valid_after`); the auth middleware rejects any token whose `iat` predates it. A stolen token no longer stays valid until expiry after logout/password reset.
- **Password Hashing**: bcrypt cost factor of 12.
- **Two-Factor Authentication (TOTP)**: Opt-in RFC 6238 authenticator codes with single-use backup recovery codes; login is a two-step flow gated by a short-lived `mfa_challenge` token that **cannot itself authenticate a session** (the second factor can't be skipped). Codes are anti-replayed (one-time-use per time-step, atomic compare-and-set), and the second factor has its **own** lockout bucket separate from the password bucket (so an attacker who knows the password can't reset the throttle by logging in). **Enrolment requires the account password**, not just the session cookie: `POST /auth/mfa/setup` **and** `/enable` both re-check `currentPassword` through the same throttled sudo helper as the self-service password doors. Without that, a momentarily hijacked session could enrol the attacker's authenticator and lock the owner out for good (password reset clears no `mfa_*` key), and the throttle offered no protection because `/setup` hands back the secret in clear, so the attacker's first code is always correct. The corresponding way out of a lockout is the admin route `POST /users/:id/mfa/reset` (`edit_users` + session-only + the privileged-target rule, and never on yourself). The per-IP limiter now covers the **whole `/auth/mfa` subtree for state-changing methods** — an earlier exact-path mount on `/auth/mfa` matched neither `/setup` nor `/enable`, leaving exactly those two unthrottled — while `GET /mfa/status` (polled on every account-page load) and `GET /mfa/policy` stay excluded, so a user toggling their own 2FA can't burn their own login budget. Secrets/backup-code hashes live in `user_meta` under keys the serializer always strips. An admin can additionally **enforce MFA by role** with a grace period: a required-role user is nudged during grace, then hard-blocked (except the enrolment flow) by a global gate — and only genuine API tokens are exempt, so a session JWT presented as a `Bearer` header is enforced exactly like the cookie.
- **Scoped API Tokens**: Personal access tokens (`Authorization: Bearer wjt_…`) for headless/machine clients. A token acts **as** its user but is bounded by **both** the user's live capabilities **and** the token's scope (coarse `read`/`write` or per-resource `posts:write`/`media:read`); effective permission is the intersection (least privilege), and an unrecognized scope is **rejected**, never silently widened. Only a sha256 of the 256-bit token is stored (plaintext shown once), tokens are revocable with optional expiry, and an API token can never manage tokens **nor be exchanged for an interactive session**: the one function that mints the session cookie refuses any headless request, so a leaked token cannot launder itself through `POST /auth/refresh` into a 7-day cookie that outlives its own revocation. The Bearer path is CSRF-exempt by design (no ambient cookie).
- **SSRF-Safe Outbound Webhooks**: Admin-registered webhook endpoints are delivered host-side with the same connect-time egress validation as the plugin network guard — the target IP is re-resolved and checked at connect time (blocking loopback, `169.254.169.254` metadata, RFC1918/CGNAT/ULA, etc.) on the initial request **and across redirect hops**, so a webhook URL can't be used to SSRF internal services. Payloads are HMAC-SHA256 signed.
- **CSRF (origin pinning **and** a double-submit token)**: two independent checks, both of which a state-changing request must pass. (1) **Origin pinning** — an **exact** allowed-origin match on `Origin`/`Referer`; the gateway pins `X-Forwarded-Host` to the real client `Host` (stripping any client-supplied value), so a remote attacker cannot forge the header to pass the same-origin check, and when **both** `Origin` and `Referer` are absent the unsafe request is **rejected (fail-closed)** unless it carries a real `Bearer` token (server-to-server). (2) **Double-submit token** — every session cookie is issued with a companion `wjs_csrf` cookie (32 random bytes, base64url; **not** `HttpOnly`, so same-origin JS can read it; same `SameSite`/`Secure`/`Path` as the session cookie, derived from it at the single issuing door). Any `POST`/`PUT`/`PATCH`/`DELETE` carrying the session cookie must echo that value in an **`X-CSRF-Token`** header; the comparison is length-checked and then constant-time, and a missing or mismatched token is `403 rest_csrf_token`. The origin check is a *negative* signal that depends on the browser being honest about provenance; the token is a *positive* one — only a same-origin script can READ the cookie — so neither replaces the other. `Bearer` callers are exempt (no ambient cookie authority); `GET`/`HEAD`/`OPTIONS` never require it. A session cookie that does not **verify** — expired, malformed, foreign signature — is not gated either: it authenticates nothing, so there is no ambient authority for the token to protect, gating it would answer `403` where `401` is the honest answer, and it would refuse every recovery route (sign in, finish 2FA, request a password reset, even log out) to a client whose *first* request is a mutation — an API script, a cookie jar, a stale tab carrying a pre-upgrade cookie with no `wjs_csrf` beside it and no safe request behind it. A client that loads the app first is healed instead: `ensureCsrfCookie` back-fills a token on any authenticated *safe* request, and because it runs before the JWT is verified, an **expired** session comes away with one too. The check is `verifyToken`, the same verification `authenticate` performs, so the gate never skips a cookie `authenticate` would accept. On top of that the **two steps of sign-in** — `POST /auth/login` and `POST /auth/mfa` — are exempt even with a *valid* cookie, because credentials in the body and a signed MFA challenge, not the cookie, are what authenticate them; the exemption is an exact enumerated match (`/auth/refresh`, logout and the `/auth/mfa/*` management routes stay gated), the Origin/Host allow-list still applies to both in full, and a successful sign-in rotates both cookies.
- **CORS**: In production, only configured origins (site / frontend / gateway) are allowed, instead of reflecting arbitrary origins with credentials.
- **Gateway Management Auth**: The gateway management secret is accepted **header-only** (never in the query string), compared in constant time, and the shipped public default is rejected (management endpoints return 503 until a real secret is configured).
- **Stored-XSS Hardening**: User-generated HTML is sanitized **isomorphically** — DOMPurify in the browser, `sanitize-html` on the server (SSR), both fail-closed. Built-in shortcode attribute values are escaped (`escAttr`/`escUrl`) before output. The editor page-tree (`_puck_data`) sanitizer is **value-based**: every non-HTML string leaf is run through a scheme blocker (`javascript:`/`data:`/`vbscript:`/`file:`, incl. control-char obfuscation), so URL props not in any key-name allowlist cannot carry a script URL; `_puck_data` sent as a JSON string is parsed, sanitized, and re-stringified. Shared by `posts.ts` and the WXR importer.
- **Token-Gated Metrics**: The Prometheus endpoint `GET /metrics` is **disabled (returns 404) unless a scrape token is configured** (`config.metrics.token` / `METRICS_TOKEN`); scrapes must present `Authorization: Bearer <token>`, compared in constant time (mismatch → 401). It is never exposed without a token.

### Plugin Sandbox (Isolated-Only)
- **OS-Process Isolation**: Every plugin runs in a **separate OS process** (`child_process.fork`, wrapped in a transport-agnostic Worker-like adapter — `worker_threads` itself is a **blocked** module inside plugins) and reaches core ONLY through the permission-checked `wordjs` capability bridge, RPC'd over IPC — it never touches raw `fs` / `child_process` / `dbAsync` / secrets. A crash, OOM, or heap escape is contained to the child and the host always survives. Bridge dispatch enforces an **exact method allowlist**; registration / mail-provider / notify-transport / route flow only through dedicated trust-gated IPC kinds.
- **No Trust Tier — Per-Capability Grants (default-deny)**: There is **no** trusted tier; every plugin is sandboxed and the admin grants each bridge capability individually in `/admin/plugins` (Android-style, default-deny, persisted server-side and never self-declarable). A plugin gets **nothing** until an operator approves it: activation is that approval, and it grants exactly what the manifest **declares** — the same path for **every** plugin, first-party or uploaded, and only while the plugin holds no grant record, so a revoke survives re-activation. No plugin is privileged. No plugin bypasses DB scoping, the IO Guard, or these grants.
- **Outbound-Network Confinement**: A plugin has **no** outbound network unless an admin grants the `network` capability. While not granted, `fetch`/`WebSocket` and the raw `net`/`tls`/`http`/`https`/`http2`/`dgram` modules are blocked. When granted, egress is confined to **public destinations only** by a connect-time guard that blocks loopback, link-local (incl. `169.254.169.254` cloud-metadata), RFC1918, CGNAT (`100.64/10`), IPv6 ULA/loopback, IPv4-mapped-v6, `0.0.0.0/8` (this-host), and multicast/reserved ranges; denies IPC / unix-socket paths; fails closed on unresolvable hosts; and re-validates the **actual resolved IP at connect time** (anti DNS-rebinding) and across redirect hops — so a network-granted plugin still cannot SSRF the metadata endpoint or internal services.
- **Secret Scrubbing**: Sandboxed plugins receive `config/app` and `dbAsync` views with credential-like fields stripped and core credential/role/option tables (`users`, `options`, …) refused.
- **Filesystem Confinement (IO Guard)**: A plugin's raw `fs` is monkey-patched (context-gated to plugin code) to its own dir plus a small set of safe zones — reads/writes outside are denied, secret files and the raw DB file are blocked, a per-plugin disk-write quota bounds volume, its own **published** subtree (`public/`, see *Allowlisted Plugin Asset Serving*) is read-only to it, and it can never **create, rename, or copy** a file into an executable code extension (`.js`/`.cjs`/`.mjs`/`.node`/`.wasm`/… **and `.html`**, a scanner-evasion primitive — `.html` is executable *by the browser* as a document in the site's own origin, where the CSP allows `'unsafe-inline'`). Covers the write family plus `readFile`/`readdir`/`createReadStream`/`open`/`openSync`/`opendir`/`readlink` (`open` is flag-aware). Under kernel hardening the read-only root filesystem is the OS-level backstop.
- **Isolated Themes**: A theme's optional server-side `functions.js` runs in the **same OS-isolated sandbox** as plugins (`loadIsolatedPlugin('theme:<slug>')` in `theme-engine.ts`), pre-scanned by the same AST validator and reaching core only through the same permission-checked bridge. Theme code never executes in-process on the host — this closed the former in-process-theme RCE surface.
- **Native Kernel Sandbox (default-ON, fail-closed)**: Every isolated plugin is additionally wrapped by the OS-native mechanism, including a plugin granted network access. Linux uses Landlock plus `no_new_privs` and an always-on seccomp-bpf dangerous-syscall filter; Windows uses AppContainer plus a one-process Job Object; macOS uses a deny-by-default Seatbelt profile. A **network grant changes only egress** — seccomp/Landlock IP-socket denial is relaxed on Linux, AppContainer receives only `internetClient` on Windows, Seatbelt receives outbound-network allows on macOS — while filesystem and process confinement remain. Live state is reported as `sandbox.kernel`, `sandbox.network` and `sandbox.permission` on admin `GET /health/details`.
- **Probe Discipline**: A platform name or a successful API call is **not** evidence. Each mechanism becomes `active` only after a real confined child and an unconfined control prove out-of-zone read/write refusal, process or dangerous-syscall refusal, working IPC/storage, and **both** network-policy shapes. Compiled production is fail-closed by default (`sandbox.requireHardening !== false`): failure of the host probe or of a per-plugin native launch **refuses the plugin**. Setting `requireHardening: false` explicitly permits the weaker compatibility fallback.
- **Linux Zero-Configuration Boundary**: The process applies Landlock and seccomp to itself through `/usr/bin/perl`, then `exec`s Node — no user namespace, sysctl, daemon, root privilege or separately installed launcher. Landlock scopes readable and writable paths, prevents cross-domain process access, and on ABI 6+ scopes abstract Unix sockets and signals. Seccomp rejects kernel-control, cross-process-memory, SysV IPC, signal, namespace/mount/modern-IO, anonymous-executable (`memfd_create`/`execveat`) and process-creation paths; `clone` is retained only with `CLONE_THREAD` so Node/libuv threads work, and on x86_64 the x32 ABI is rejected. Without the network grant every new socket is rejected; with it, only AF_INET/AF_INET6 client sockets are admitted (with independent Landlock TCP rules on ABI 4+).
- **Windows and macOS Homologues**: AppContainer restricts access to objects ACL'd for its package SID; its Job Object admits exactly the contained Node process and rejects descendants, while `internetClient` is the only optional capability. Seatbelt allowlists the required runtime/app reads and writable zones and denies process inspection; `process-fork`/`process-exec` are deliberately **allowed** — a descendant inherits the same Seatbelt domain, so the process tree is contained rather than forbidden. Its network profile changes independently. Neither OS pretends to have Linux namespaces or a Unix uid drop — the guarantee is **equivalent authority reduction**, not identical primitives.
- **Node Permission Model** (every compiled platform, default-ON, probe-gated): An additional C++ capability floor **underneath** the native sandbox, not a substitute for it. Filesystem access is scoped and `child_process`, `worker_threads`, native addons and WASI are never granted. It does **not** enforce network policy.
- **Layered Resource Limits**: Windows has preventive per-plugin Job Object **memory and process** limits, plus an **opt-in** CPU-rate cap (`sandbox.cpuQuotaPercent`, default `0` = off — the same knob as the Linux quota). Linux has the same preventive guarantees when the optional cgroup v2 scope is available (`sandbox.useCgroupMemoryCap`), plus `RLIMIT`/RSS backstops; macOS keeps process separation, the V8 heap cap and reactive RSS enforcement. **CPU is bounded by default wherever no preventive cap is installed** — Windows, a plain Linux launch, macOS, a host whose cgroup probe failed — reactively, by a default-on watchdog that `SIGKILL`s a child holding ≥ 95% of one core for `sandbox.cpuBurstSeconds` (default 60 s) without a single quiet tick, naming the reason on the health surface (it samples Linux `/proc/<pid>/stat`, macOS `ps -o cputime=` and Windows the `CPU Time` column of `tasklist /V`). The preventive caps — `cpuQuotaPercent` on Windows and inside the Linux cgroup scope — remain **opt-in**, and where one is installed the watchdog stands down.

### Vulnerability Management
- **Deep Static Analysis (SAST)**: AST-based (Acorn) scanning of plugins at install to block Injection, RCE, and Obfuscation. Parse failures are treated as violations (**fail-closed**). The scan runs at install, at activation and at boot for every active plugin, and it now also walks the dependency tree a plugin **ships** (`node_modules/`) — bounded to 4,000 files, 1 MB per file and 32 levels of depth, `.js`/`.cjs`/`.mjs` only, with no symlink followed outside the plugin directory (every path resolved with `realpath`). Hitting a bound, an escaping symlink, or an unparseable dependency file is itself **reported as a finding**, not a pass. Runtime containment (`secure-require`, the IO Guard, the worker's ESM hook, `blockCodeGen`) remains what actually *stops* a dependency; this pass buys the operator a look.
- **Dependency Conflict Check**: Strict SemVer verification to prevent plugin dependency collision.
- **Safe Dependency Install**: Plugin dependencies are installed with `execFile` and an argument array (no shell string), so manifest dependency names cannot inject shell commands.
- **License Gate (CI)**: `license-checker --production` fails the build on `AGPL`/`SSPL` dependencies (WordJS is MIT; see `THIRD-PARTY-NOTICES.md`).
- **Supply-Chain Transparency**: CodeQL static analysis (SAST) runs on every pull request, a per-release **CycloneDX SBOM** is generated and attached to each GitHub Release, third-party GitHub Actions are pinned to immutable commit SHAs (`anchore/sbom-action`, `softprops/action-gh-release`; the GitHub-owned `actions/*` and `github/codeql-action/*` ride major tags), and `.github/dependabot.yml` opens **weekly version-update PRs** across all six npm workspaces (`/`, `/backend`, `/gateway`, `/frontend`, `/setup`, `/packages/create-wordjs`) plus GitHub Actions. What catches an *advisory* is **CI, not Dependabot**: Dependabot alerts and Dependabot security updates are **not enabled** on the repository (they are a repository setting the owner may switch on in *Security & analysis*, and doing so would add a second, independent advisory feed — nothing here replaces them). The advisory checks that live in the tree, and therefore travel with any clone or fork, are both built on the same wrapper, `scripts/ci-audit.mjs` (`npm audit --omit=dev --audit-level=high`, which blocks on a real high/critical production-dependency advisory and treats a confirmed npm advisory-service outage as *audit unavailable* — retried, then warned, never a silent pass):
  - a **push-time gate** in `ci.yml` and `release.yml`, which blocks the build and the release in `backend`, `gateway`, `frontend` and `packages/create-wordjs`; and
  - a **daily scheduled sweep**, `.github/workflows/dependency-audit.yml` (04:41 UTC, plus manual `workflow_dispatch`), which runs that same gate across **all six** workspaces — `/` and `/setup` included, which no push-time job installs — and, on any failure, opens or comments on a `Dependency audit failed (<date>)` issue naming the affected workspaces and linking the run. This is the part the push-time gate cannot cover: an advisory published against a dependency we already ship changes nothing in our source, so without the timer it would go unnoticed until somebody happened to push.
- **Sandbox Parity Verification**: `.github/workflows/sandbox-parity.yml` builds the production code and runs `backend/scripts/verify-sandbox-parity.mjs` on current **and older** Linux runners (`ubuntu-latest`, `ubuntu-22.04`) plus one macOS (`macos-14`) and one Windows (`windows-latest`) runner. The verifier imports the **same compiled modules WordJS launches**, so a duplicate probe cannot certify a primitive the product never uses.

### Known Limitations
- **CSP is not an XSS backstop yet**: the production `script-src` still carries `'unsafe-inline'` (the Next.js App Router's inline bootstrap — a per-request nonce is the documented follow-up), `https:` (solely the bundled `analytics-tag` plugin's third-party tags, including an **admin-entered Matomo origin** that a build-time header cannot allow-list) and `blob:` (plugin admin bundles). The XSS control is the server-side sanitizer, not this header.
- **CSRF token scope**: the double-submit token is a per-browser random value rather than one bound to the session secret, and it rotates when a session cookie is issued rather than per request. A request that presents no **verifiable** session cookie is not gated at all — correctly, since it carries no ambient authority — but that also means the token is not an anti-automation control (the control itself is described under Active Defenses).
- **Resource limits**: macOS has no unprivileged **preventive** resident-memory primitive; process separation, the V8 heap cap and reactive RSS enforcement are what remain there. The preventive CPU quota (`sandbox.cpuQuotaPercent` — one knob, spelled as a Windows Job Object rate cap or as `CPUQuota` inside the Linux cgroup scope) is **opt-in**, and the default-on reactive CPU watchdog **bounds** a burn rather than preventing it. **Linux cgroup mode enabled without that quota is the one configuration with no CPU bound at all**: the child the host can see is `systemd-run`, not the node process, so the watchdog cannot sample it — the server warns at launch and names the knob.
- **Host requirements**: Linux needs Landlock (kernel 5.13+) and `/usr/bin/perl`; a host without either refuses isolated plugins by default. The Windows source-only `ts-node` **development** worker is exempt from AppContainer because recursively provisioning ACLs over its TypeScript dependency tree exceeds development test deadlines — compiled production is not exempt.
- **Dependency scan is bounded**: a shipped `node_modules/` beyond 4,000 files, 1 MB per file or 32 levels of depth is refused rather than scanned (the refusal is reported as a finding, never as a pass). Inside a dependency several name-based detectors are deliberately relaxed, so runtime containment — not this scan — is what actually stops a dependency.
- **Gateway and backend CSPs are permissive mirrors**: both carry an open `img-src`/`connect-src` (`*`) — the structural directives (`frame-ancestors 'self'`, `base-uri 'self'`, `form-action 'self'`, `object-src 'none'`) are present, Helmet's defaults filling in what the config does not name — and each governs only the responses that origin generates itself — a proxied response keeps the upstream's own policy.
- **No independent audit yet**: see the posture note above.

## 🐛 Reporting a Vulnerability

If you discover a security vulnerability within WordJS, report it through **GitHub's private vulnerability reporting**, which is enabled on this repository: <https://github.com/jaimemartinez/wordjs/security/advisories/new> (reachable from the repo's **Security** tab). That is the only private channel — the project publishes no security email address.

**Do NOT open a public GitHub issue.** Blank issues are disabled, and the issue chooser (`.github/ISSUE_TEMPLATE/config.yml`) deliberately offers a link to this security policy instead of a bug-report form.

### Response Time
WordJS is primarily solo-maintained (see the posture note above), so these are **targets, not a guaranteed SLA**:
- **Acknowledge**: 24-48 hours.
- **Fix**: 72 hours for a critical issue. A fix lands on `main` first and reaches users in the next tagged release (see Supported Versions).

## 📝 Supported Versions

WordJS is pre-production; only the latest `main` and the current `2.x` release line are supported. There is no LTS line yet.

| Version   | Supported | Notes                                              |
| :-------- | :-------- | :------------------------------------------------- |
| `main`    | ✅         | Latest development line (the only one patched)     |
| `2.x`     | ✅         | Current release line (latest tag and latest GitHub Release: `v2.1.0`) |
| < `2.0`   | ⚠️        | Best-effort; upgrade to `2.x` or latest `main`     |

> **There is no maintenance branch and there are no backports.** `2.x` is a tag line, not a branch —
> a fix is committed to `main` and reaches users in the next tag cut from `main`. If you need a fix
> before that tag exists, run `main`.
>
> **Do not read the diff between a release tag and `main` as a commit range.** The public history was
> rewritten, so no tag up to and including `v1.14.1` is an ancestor of `main` (`git merge-base
> --is-ancestor v1.14.1 main` fails; their common ancestor is a January 2026 commit). Those tags still
> point at the pre-rewrite history, and the same release commit exists under two different SHAs.
> `v2.0.0` and later are cut from the current history and *are* ancestors of `main`. Compare a pre-2.0
> release by `CHANGELOG.md` and by content, not by `git log v1.14.1..main`.
